# Product analytics

NyxID's optional product analytics uses authenticated account UUIDs. It is separate from security audit, billing, essential operational records and push delivery. Those records do not depend on product-analytics consent. Implemented controls and outstanding erasure work are described in [the implemented controls document](SECURITY_REMEDIATION_W1_W4.md); this document describes the current source contract.

Nyxbot failures use `nyxbot.error` through the same authenticated relay. See
[Nyxbot error telemetry](NYXBOT_ERROR_TELEMETRY.md) for codes and coverage.

## Permission and dispatch

An account's `profile_config.analytics` is default off. An authenticated first-party human can read or change it with `GET` or `PUT /api/v1/users/me/preferences/analytics`. A mutation includes its expected `account_id`; the server checks it against the authenticated subject before writing. Each explicit choice stores the server's policy version (`"1"`) and a database-generated change time, and receives a new random revision even when the boolean is unchanged. Older records without a policy version retain an unknown version; the server does not invent a historical acknowledgement. Responses are `no-store`.

Account permission is necessary on every surface. A device's account-bound local choice and DNT can only narrow it. A surface/version header classifies a request; it grants no permission. Authenticated requests eligible for analytics carry both `X-NyxID-Analytics: enabled` and `X-NyxID-Analytics-Account` matching the authenticated actor. Agent/API-key activity cannot acquire analytics permission merely from its surface header. Anonymous and partially authenticated login/MFA events are denied. A full-login event needs an explicitly authenticated context; pre-auth contexts remain denied after reconstruction.

`TelemetryClient::track` performs bounded admission: at most 1,024 concurrent reads, a 250ms overall timeout, and a 1,024-event in-memory queue. The gate reads the indexed person record from the primary with linearizable read concern and bounded `maxTimeMS`. Consent changes use majority writes. There is no positive consent cache. Unknown, disabled, missing, deleted, unavailable or mismatched accounts fail closed. Admission captures the authorized revision; the drain checks that same revision afresh immediately before vendor dispatch. Queued work cannot inherit a later opt-in after withdrawal or regrant. A request already sent to a vendor cannot be recalled; the final check precedes that network request.

The asynchronous `emit_event` and `track` APIs await admission, which may take up to 250ms. Product handlers do not wait for vendor delivery. Queue overflow and read failures drop optional events; they do not block the product operation or create a persistent analytics backlog.

Private API CORS permits `X-NyxID-Client`, `X-NyxID-Client-Version`, `X-NyxID-Analytics`, `X-NyxID-Analytics-Account` and `DNT` from configured origins. This support is implemented; these headers classify or narrow requests and never grant account permission. Earlier telemetry rollout observations belong to the [dated planning record](TELEMETRY_CONSENT_FIX.md), not current deployment instructions.

## Client controls and account isolation

Web and mobile events use `POST /api/v1/users/me/analytics/events` through NyxID. Every explicit client event obtains fresh account permission and submits the expected account and revision. Each client allows at most 16 concurrent admissions. Account, session and local-choice generations invalidate pending events after logout, account switch, withdrawal or shutdown. Clients do not send directly to PostHog, create anonymous analytics identities, replay sessions, autocapture DOM/screens or transmit raw exceptions.

Web Settings has independent account and device controls, loading/error state and a permission retry action. Local OFF remains available during server failure. Browser DNT and Global Privacy Control narrow collection. Local choices use separate records per account. Cross-tab synchronization reads current storage without writing it and invalidates pending events even for delayed/out-of-order notifications. A delayed account opt-in response cannot overwrite a newer device choice. A failed local withdrawal remains denied in the current session; Settings reports a persistence failure so the user can retry. Legacy unbound positive preferences are not assigned to a logged-in account.

Mobile Settings exposes the same two controls and retries. Local choices are bound to accounts. Successful device persistence acknowledges the existing choice without cancelling an account toggle awaiting the server; failed writes invalidate that pending choice. Failed device writes retain a session denial for the captured account and expose an unsaved-state retry; they never change a successor account. SecureStore auth writes are serialized, and refresh commits compare the captured session generation and credentials. An old refresh cannot overwrite a newer login or logout. Requests recheck authority after response/body work and before refresh, retry or session invalidation.

CLI controls retain `nyxid telemetry enable|disable|status`, with `--profile` supported before or after the telemetry subcommand. `account-enable|account-disable` separately change account permission. Device choices bind the normalized full deployment base URL (including a path prefix), saved human account and profile. Command events capture login generation and local-choice revision at command start and recheck after the command and around admission. Requests recompute device headers from disk, allowing another process's `telemetry disable` to stop future admissions. Analytics-control commands emit no command event. No CLI DSN is needed for this authenticated relay.

`DO_NOT_TRACK` and `NYXID_TELEMETRY=off` deny CLI collection. `NYXID_TELEMETRY=on` only permits consulting an explicit account-bound choice; it grants neither device nor account permission and cannot override a bound withdrawal. Historical config positives do not create a new account-bound positive. There is no automatic anonymous first-run prompt.

## Event data and limits

The server maintains the authoritative runtime taxonomy in `backend/src/telemetry/client_event.rs`; the web/mobile TypeScript schemas provide caller typing. Relay requests are limited to 8KiB before JSON allocation. Events are limited to 4KiB and 12 properties, with known event names, field-specific finite values and bounded numeric/boolean types. Unknown event names, vendor control keys and unknown top-level fields are rejected. Dynamic URLs, hostnames, slugs, entry-point labels, form fields and free text are omitted rather than accepted as arbitrary strings. Adding a category requires an explicit server taxonomy update.

Backend typed event properties use `backend/src/telemetry/schema.rs`, then the egress scrubber. Surface, application version, environment and optional client version are added centrally. Raw credentials, authorization headers, MFA/recovery codes, request bodies, form contents, messages, search terms and raw exceptions must not be added to events. Scrubbing is defense in depth, not permission or an anonymity guarantee. Backend event callers remain subject to inventory and review as features change.

Mobile social MFA exemptions emit the typed `auth.mobile_mfa_exempted` event
with only `mfa: skipped_mobile_rollout`. It uses the existing account permission
and pre-authentication gates; this rollout does not grant analytics permission.
Redirect login records a metadata-only `social_login` audit independently.

Social token exchange emits `auth.token_exchanged` with the short canonical `subject_token_type` (`id_token` or `access_token`) and `exchange_provider` after successful provider verification, using the exchanged person as the subject. A rollout exemption also emits `auth.mobile_mfa_exempted`. Both use the existing device/account consent gates: pre-auth protocols and missing/disabled consent do not dispatch account-linked events. The native exchange writes one `social_token_exchange` audit with provider, client, session and MFA outcome; redirect login retains its `social_login` audit.

The backend's `telemetry::dispatch_inventory_tests` enumerates direct `track` calls, durable dispatch admission, queue-job construction and vendor capture endpoints across Rust source, including test callers. A new call site fails the inventory test until its consent boundary has been reviewed. Runtime regressions separately exercise the live database and vendor boundary, including withdrawal across independent app states sharing a database, database failure and device restrictions. Product-analytics denial does not suppress security audit writes.

## Server configuration

`NYXID_TELEMETRY_DSN` selects the operator's PostHog ingestion project; `NYXID_TELEMETRY_HOST` selects its ingest host. The built-in default is `https://us.i.posthog.com`. `NYXID_SHARE_ANALYTICS` is an alternative operator configuration. Without a configured backend destination no product event dispatches. A configured destination never grants account or device permission. Public configuration may describe availability to clients; it supplies no consent authority.

Operators must establish their own deployed-provider register, disclosures, processing locations, retention windows, contracts and transfer arrangements. Source defaults do not prove legal roles, contracts or regional processing. Security logs and database/backups have separate retention arrangements.

## Erasure status

The current erasure draft uses `NYXID_TELEMETRY_ERASURE_DESTINATIONS`, an explicit JSON array of current and historical PostHog project APIs with personal API keys. Each entry contains `id`, an HTTPS-origin `api_host`, numeric-string `project_id`, and `personal_api_key`. Keys remain in runtime configuration; checkpoints retain destination identifiers and vendor person UUIDs. Registry identifiers cannot be rebound to a different project. Removing runtime credentials preserves the historical destination and leaves its jobs awaiting operator action.

The account workflow retains a parent intent even with no configured destination. A bounded resumable scan discovers legacy jobs, including completed children without parents. Parents fan out idempotently to retained destinations, and reopen when a historical destination is registered later. Completion is relative to that registry inventory; incomplete historical configuration cannot establish that all vendor data has been erased. Admin and self deletion enqueue centrally. Vendor dispatch waits until the local account is absent and no durable capture remains in flight or uncertain.

The worker looks up the person UUID, requests person deletion with `delete_events=true` and `delete_recordings=true`, and verifies a new asynchronous deletion-status record. Empty HTTP 202 means accepted, not completed. Previous completed status rows are not fresh evidence. Before accepting completion it looks up the distinct ID again; a recreated person reopens deletion. Leases use database time and a random fence; a worker can reclaim an expired lease, and stale workers cannot update checkpoints. Polling runs every 30 seconds in batches of at most 16. Failed operations use capped backoff up to one hour; uncertainty is retained rather than silently exhausted.

Analytics dispatch records durable intent before HTTP submission and settles successful provider receipt. Confirmed acceptance removes the per-event row and retains one account checkpoint, avoiding an unlimited accepted-event history. That checkpoint is not processing-drain evidence. Crash, timeout or an unconfirmed database settlement leaves uncertainty; elapsed time alone does not prove a provider discarded a request. The local `nyxid-server telemetry-erasure status` command lists bounded job and uncertain-dispatch status. `bind-person` supplies a historical vendor UUID; `attest-no-data` requires operator identity, evidence and a reason covering events and recordings as well as person lookup. `attest-dispatch-drained` reconciles an uncertain transport with evidence; `attest-account-drained` records provider processing evidence bound to the account's latest admitted generation before erasure resumes. Any later admission invalidates earlier processing-drain evidence. These actions record durable operator evidence and distinguish operator attestation from vendor-verified completion. An empty lookup by itself never proves historical deletion.

**Validation boundary:** this replacement is an unvalidated implementation draft pending Rust/MongoDB/vendor-fixture regressions. Its protocol follows the [PostHog deletion API](https://posthog.com/docs/privacy/data-deletion); a provider may process accepted capture asynchronously beyond transport acknowledgement. Operators must verify processing/drain and historical project coverage under the configured provider's actual contract. No universal external erasure deadline or provider guarantee is inferred from local HTTP success. Enqueueing or accepting a job alone is not completion.

Audit/billing evidence is retained under its integrity contract. No account-erasure task may add an unsafe audit TTL, scrub or re-sign historical chains. Changes to retention require preserving that integrity contract.

Dispatch reconciliation retains at most 32 unresolved requests per account. At that limit new product capture fails closed until existing requests settle or an operator records evidence; uncertainty is never discarded on lease expiry. Confirmed transport acceptance removes the per-event row and retains one account generation checkpoint. This bounds event-row growth while preserving provider-processing uncertainty.

A provider deletion status outside its documented `pending`/`completed` states, including an explicit failure, marks the destination job `operator_action` with a stable error code. The worker never reports that as accepted or complete. After investigating the provider, `telemetry-erasure bind-person` with the verified UUID, operator identity and evidence reference records reconciliation and starts a fresh request with a fresh status baseline. `attest-no-data` is reserved for independently evidenced absence, not a workaround for failure.
