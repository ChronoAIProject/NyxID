# NyxID In-Chat Connect Adoption Plan

## 1. Recommendation

Use a first-class, typed `connect_card` block in the Aevatar assistant message, carried on the existing chat POST's SSE response and returned in conversation history. The block should use NyxID's already-shipped `ConnectCardContentBlock`, with Aevatar's opaque `block_id`, canonical `catalog_slug`, and an exact `key_id` for reauthorization; the FE must re-resolve action metadata from NyxID's catalog and completion state from NyxID's keys API before acting. Ean's model-authored `nyxid:connect` fence works without a backend message-schema change and reloads from flat history, but malformed/model-injected JSON, ordinal IDs, and prose parsing make it a brittle production protocol (`public/blocks.js:3-9`, `public/blocks.js:78-97`, `public/app.js:1514-1521`). The typed choice requires an Aevatar producer/storage change, but Aevatar already produces a validated structured blocker (`frontend/src/lib/assistant/aevatar-transport.ts:117-126`, `frontend/src/lib/assistant/aevatar-transport.ts:538-568`), so persisting that information as the existing block is the smallest reliable production path. After NyxID reports every required card satisfied, the FE should resume through the normal chat-message POST; a reload-safe exactly-once experience additionally requires Aevatar to accept a caller-supplied stable idempotency ID and expose durable acceptance. No connect signal, catalog, credential, or FE-selected key is sent to Aevatar.

## 2. How Ean's Prototype Does It

### Detect and parse

- The assistant/LLM embeds a fenced code block whose exact info string is `nyxid:connect`; all other assistant output remains Markdown (`public/blocks.js:1-8`). The server prompt explicitly teaches the model to emit JSON containing a catalog slug and reason (`server.mjs:580-608`). That prompt-injected service catalog is excluded from adoption by hard constraint 2.
- `splitMessageSegments` scans the assistant text line by line, splits normal text from connect fences, and emits a `pending_card` placeholder for an unfinished fence while streaming (`public/blocks.js:20-76`).
- `parseConnectSegment` parses the fence body as JSON, accepts `catalog_slug` or `slug`, validates the slug, truncates `reason` and `requested_scopes`, and synthesizes `connect:<slug>:<ordinal>` as the card key; malformed JSON or slug falls back to visible code text (`public/blocks.js:78-97`).
- There is a second live-only path: a service-authorization blocker calls `addConnectCardForMissingService`, which constructs a connect segment directly when its slug is in the available connector snapshot (`public/app.js:2462-2469`, `public/app.js:2490-2509`).

### Resolve display and connection data

- The browser fetches `/api/nyxid/connectors`; the BFF obtains NyxID `GET /api/v1/keys` and `GET /api/v1/catalog`, caches the join, and returns connected and available services (`public/app.js:571-592`, `server.mjs:514-532`).
- `deriveConnectors` groups keys by `catalog_service_slug`, derives status and auth kind, and emits remaining catalog entries as available connectors (`server.mjs:455-511`).
- `buildConnectCardBlock` joins the parsed slug to that snapshot and produces a NyxID-shaped `connect_card` with service copy, icon, auth kind, connection state, instructions, steps, and footer (`public/blocks.js:100-133`).

### Render

- `createConnectCard` holds local status, busy/error state, the original-request retry context, and a DOM root; it builds and renders the card immediately and registers it for later refreshes (`public/app.js:594-617`).
- `renderAssistantSegments` renders text as sanitized Markdown, cards as rich DOM, and partial fences as a loading placeholder (`public/app.js:916-940`). Live text is reparsed on each delta and once at completion (`public/app.js:2255-2279`).
- The card anatomy is service identity plus status, a three-step authorization/brokering/resume ledger, inline action/error/success areas, and a security footer (`public/app.js:760-817`, `design/nyxid-assistant-shell.html:833-880`). The implementation CSS supplies the header, step rail, action zone, credential form, success/error states, and footer (`public/styles.css:903-1076`, `public/styles.css:1128-1220`).

### Act by auth kind

- `api_key`: the card opens a masked inline form and submits the credential to the prototype BFF only (`public/app.js:819-865`, `public/app.js:645-676`); the BFF forwards it to NyxID `POST /api/v1/keys` and clears its connector cache (`server.mjs:541-568`). The secret does not enter the chat request.
- `oauth`: the prototype does not implement an in-card provider flow. It opens NyxID `/keys?slug=<slug>` in another window and marks the local card `waiting_for_user` (`public/app.js:619-643`, `public/app.js:885-897`).
- `device_code`: it follows the same NyxID deep-link path as other non-API-key auth; the prototype does not display or poll a device code itself (`public/app.js:825-826`, `public/app.js:885-897`).

### Observe completion and resume

- A successful inline API-key POST immediately marks the card connected (`public/app.js:645-669`). External OAuth/device completion is checked only when the user presses the refresh action, which forces a fresh connector read; this is not automatic status polling (`public/app.js:678-695`, `public/app.js:899-904`).
- Any connector refresh updates all mounted cards; a matching connected slug calls `markConnectCardConnected` (`public/app.js:729-747`).
- `sendPrompt` captures the original prompt/attachment on the run (`public/app.js:1588-1609`). Once a card becomes connected, `scheduleConnectCardRetry` waits 900 ms and resends that captured request if the same conversation is active and no run is in progress; otherwise it asks for a manual retry (`public/app.js:697-727`).

### Reload/history behavior

- Stored assistant messages contain the original raw text. `renderStoredMessage` reparses that text, so a fenced card reappears after reload (`public/app.js:1514-1526`).
- Reloaded cards receive a new empty registry and no retry context, so their state can be enriched from the current connector snapshot but they cannot automatically resume the original request (`public/app.js:1518-1521`, `public/app.js:710-713`).
- The direct authorization-blocker card is appended only to live DOM/state and is not encoded into stored assistant text, so that fallback does not inherit the fence path's reload behavior (`public/app.js:2490-2509`).

## 3. What NyxID Has Today

### Already sufficient or directly reusable

- The production type already implements the Draft v8 field set and adds optional `reason_code`: identity, canonical slug, display fields, auth kind, scopes, key/device fields, state/error, steps, and footer (`frontend/src/types/assistant.ts:1-7`, `frontend/src/types/assistant.ts:34-57`, `nyx-chat-prd.md:162-182`). Do not create a second UI card model unless a narrow wire DTO is needed at the transport boundary.
- `ChatThread` already dispatches a typed `connect_card` block to `ConnectCard` and safely renders unknown block types as unsupported content (`frontend/src/components/assistant/chat-thread.tsx:12-19`, `frontend/src/components/assistant/chat-thread.tsx:42-69`).
- `ConnectCard` already finds a key by exact `key_id` or canonical `catalog_service_slug`, recognizes live active keys, distinguishes reauthorization, opens the shared dialog for a missing service, and routes non-OAuth credential management to key detail (`frontend/src/components/assistant/blocks/connect-card.tsx:35-78`, `frontend/src/components/assistant/blocks/connect-card.tsx:98-133`).

- The existing connector derivation uses the correct join key, `catalog_service_slug`, and separates connected keys from catalog entries not yet connected (`frontend/src/lib/assistant/plugins.ts:123-159`). Reuse that invariant; do not join on the user-facing proxy slug.
- `AddKeyDialog` already accepts a preselected slug/reconnect key and resolves the actual catalog entry itself (`frontend/src/components/dashboard/add-key-dialog.tsx:2274-2293`, `frontend/src/components/dashboard/add-key-dialog.tsx:2364-2405`). It already routes catalog entries to OAuth, device-code, or credential flows (`frontend/src/components/dashboard/add-key-dialog.tsx:2429-2465`).
- API-key creation already goes through `useCreateKey`/NyxID `POST /keys` (`frontend/src/components/dashboard/add-key-dialog.tsx:2582-2648`). OAuth already creates/reuses a placeholder and calls NyxID's provider initiate endpoint with the key ID and scopes (`frontend/src/components/dashboard/add-key-dialog.tsx:1441-1468`, `frontend/src/hooks/use-providers.ts:105-175`).
- The live transport already accepts only the exact structured `CUSTOM nyxid.authorization.required` blocker with a canonical slug and two reason codes, redacts its display message, and constructs the existing card type (`frontend/src/lib/assistant/aevatar-transport.ts:534-568`, `frontend/src/lib/assistant/aevatar-transport.ts:1593-1596`, `frontend/src/lib/assistant/aevatar-transport.ts:1967-2037`). It generates a random FE block ID and deduplicates by slug only inside one running turn (`frontend/src/lib/assistant/aevatar-transport.ts:313-315`, `frontend/src/lib/assistant/aevatar-transport.ts:1977-1984`, `frontend/src/lib/assistant/aevatar-transport.ts:2002-2008`, `frontend/src/lib/assistant/aevatar-transport.ts:2035-2037`), so retain it only as a live compatibility adapter without reload or automatic-resume guarantees.

### Present but incomplete for this flow

- History is currently a flat `content: string` model, and `historyEntryToMessage` converts every entry to one text block; live synthetic cards therefore disappear when the transport is reconstructed/reloaded (`frontend/src/lib/assistant/aevatar-transport.ts:233-241`, `frontend/src/lib/assistant/aevatar-transport.ts:382-401`).
- The live blocker does not carry actionable catalog metadata, so the transport installs `auth_kind: "api_key"` only as a display default; the card must resolve real auth behavior from NyxID's catalog (`frontend/src/lib/assistant/aevatar-transport.ts:2002-2021`).
- `ConnectCard` reacts to an active key, but its connected copy tells the user to send the request again and it exposes no completion callback (`frontend/src/components/assistant/blocks/connect-card.tsx:59-75`, `frontend/src/components/assistant/blocks/connect-card.tsx:30-34`).
- `AddKeyDialog` exposes only open/prefill/reconnect props, not `onConnected` or a chat mode (`frontend/src/components/dashboard/add-key-dialog.tsx:2274-2291`). Its normal success path proceeds to an Agent Key/setup step and closes only when that step calls Done (`frontend/src/components/dashboard/add-key-dialog.tsx:2899-2906`, `frontend/src/components/dashboard/connect-verify-step.tsx:65-88`); that extra onboarding is not needed to let Aevatar use an already provisioned NyxID connection.
- OAuth currently hard-redirects the whole tab to the provider and returns to `/keys/{id}`, so it is not an in-thread completion flow (`frontend/src/components/dashboard/add-key-dialog.tsx:1454-1469`, `frontend/src/lib/navigation.ts:8-13`).
- Device-code success invalidates provider/LLM queries but not `['keys']`, even though the card's connected state comes from `useKeys` (`frontend/src/hooks/use-providers.ts:217-239`, `frontend/src/components/assistant/blocks/connect-card.tsx:59-65`).
- The assistant page supplies approval callbacks to `ChatThread` but no connection-complete/resume callback (`frontend/src/pages/assistant.tsx:145-158`).

### FE <-> Aevatar: chat and history only

**Assistant message shape.** Aevatar emits a normal assistant message with `schema_version: 1` and an ordered typed block array, matching the existing message envelope (`frontend/src/types/assistant.ts:109-125`). A missing service is represented by the existing full `connect_card` shape (`frontend/src/types/assistant.ts:34-57`), for example:

```json
{
  "id": "assistant-message-id",
  "role": "assistant",
  "schema_version": 1,
  "blocks": [
    {
      "type": "connect_card",
      "block_id": "opaque-aevatar-id",
      "catalog_slug": "api-github",
      "service_name": "GitHub",
      "icon_url": "",
      "subtitle": "Required to read the requested repositories",
      "auth_kind": "oauth",
      "requested_scopes": ["repo"],
      "key_id": null,
      "granted_scopes": null,
      "device_user_code": null,
      "device_verification_url": null,
      "state": "needs_connection",
      "error_message": null,
      "steps": [],
      "footer": "Brokered by NyxID",
      "reason_code": "NYXID_SERVICE_NOT_CONNECTED"
    }
  ],
  "created_at": "2026-07-23T00:00:00Z"
```

The shipped type implements the Draft v8 field set and adds optional `reason_code` (`frontend/src/types/assistant.ts:34-57`, `nyx-chat-prd.md:162-182`). Contract authority is narrower than the shape:

| Field | Authority and FE behavior |
|---|---|
| `type`, `block_id` | Aevatar-owned type/opaque identity. The FE deduplicates and patches by `block_id`; it never parses the ID. Typed event reduction already keys start/update/completion this way (`frontend/src/lib/assistant/stream.ts:56-82`, `frontend/src/lib/assistant/stream.ts:122-166`). |
| `catalog_slug` | Required canonical NyxID catalog lookup key. The FE validates it against NyxID catalog before enabling an action; current key/catalog joins already use `catalog_service_slug` (`frontend/src/lib/assistant/plugins.ts:123-159`). |
| `service_name`, `icon_url`, `subtitle`, `steps`, `footer`, `error_message` | Untrusted display hints: sanitize/render only. Prefer NyxID catalog name/icon/instructions when available. The current blocker parser already redacts model/upstream display text (`frontend/src/lib/assistant/aevatar-transport.ts:554-568`). |
| `auth_kind`, `requested_scopes` | Hints, never endpoint selectors. The FE derives provider type/config and allowed scopes from the catalog and rejects unknown slug or invalid requested scope; the catalog exposes provider/auth/scope metadata (`frontend/src/types/keys.ts:144-177`). |
| `key_id` | Optional for `NYXID_SERVICE_NOT_CONNECTED`; required producer identity for `NYXID_UNAUTHORIZED`. A missing-service card completes when any active key matches `catalog_slug`; an unauthorized card completes only when this exact key becomes active/authorized. Current card matching is exact-key-first and deliberately does not let a same-slug active key satisfy reauthorization (`frontend/src/components/assistant/blocks/connect-card.tsx:38-65`). The FE never sends a selected key ID to Aevatar. |
| Device fields | Optional display/history hints only; resolve live device-code state from NyxID provider responses, as the existing dialog does (`frontend/src/components/dashboard/add-key-dialog.tsx:1694-1777`, `frontend/src/components/dashboard/add-key-dialog.tsx:1936-2059`). |
| `state`, `reason_code` | Aevatar's persisted turn state plus FE overlay. `NYXID_SERVICE_NOT_CONNECTED` means create; `NYXID_UNAUTHORIZED` means reauthorize/manage. The current target already distinguishes those reason codes (`frontend/src/components/assistant/blocks/connect-card.tsx:43-58`). |

**Delivery, validation, and persistence.** On the same POST that sends user chat and returns SSE, Aevatar emits the card as a typed presentation block, not as text. Conversation detail history returns that same typed block so reload does not depend on a fence parser. The Draft v8 already states that typed blocks, the content POST stream, and detail history are the intended boundary (`nyx-chat-prd.md:64-80`, `nyx-chat-prd.md:101-117`, `nyx-chat-prd.md:143-147`). At both history hydration and typed `block.started`/`block.completed` boundaries, the FE runtime-validates `schema_version`, discriminants, required fields, slug/state/auth enums, arrays, URLs, and bounded string/array sizes. Unknown or malformed input becomes the existing unsupported-content shell; it is never cast directly into a React component, as the current renderer does after checking only `type` (`frontend/src/components/assistant/chat-thread.tsx:12-18`, `frontend/src/components/assistant/chat-thread.tsx:42-68`). During migration, `nyxid.authorization.required` may synthesize a live-only fallback. A first-class typed card wins for the same slug and replaces/causes the synthetic card to be ignored; its random synthetic ID is never a resume-group identity (`frontend/src/lib/assistant/aevatar-transport.ts:1977-1984`, `frontend/src/lib/assistant/aevatar-transport.ts:2002-2008`). Typed history is required for reload-safe automatic resume.

**Completion and resume.** A connect click never invokes Aevatar. For `NYXID_SERVICE_NOT_CONNECTED`, the card is satisfied when NyxID returns any active key with the same `catalog_service_slug`; for `NYXID_UNAUTHORIZED`, only the Aevatar-supplied exact `key_id` becoming active/authorized satisfies it (`frontend/src/components/assistant/blocks/connect-card.tsx:38-65`). When every card in the latest blocked assistant message is satisfied, the FE resends the nearest preceding user text through the ordinary chat POST. Reload-safe once-only delivery requires a stable conversation/card-group idempotency ID supplied by the FE and durably deduplicated by Aevatar; current transport instead mints a random ID inside each run and history exposes no client request ID (`frontend/src/lib/assistant/aevatar-transport.ts:233-241`, `frontend/src/lib/assistant/aevatar-transport.ts:1040-1049`). Aevatar must return that ID in history or define an already-accepted/duplicate response. Without that guarantee, automatic resume is best-effort and the card retains a visible manual retry. Aevatar re-reads `GET /api/v1/keys` itself and continues the task. No `card_action`, signals, approve, connect, key-status, or service-catalog call is made from FE to Aevatar. Ean's captured-request resend is the behavioral precedent (`public/app.js:710-727`, `public/app.js:1602-1609`), while the target already sends a message and receives its SSE in one POST (`frontend/src/lib/assistant/aevatar-transport.ts:1100-1166`).

**Reload.** History supplies the typed card; the FE re-resolves it against current catalog and keys. Auto-resume is eligible only when the latest assistant turn is blocked on connection, no later user message exists, every card in that gate is satisfied under the reason-specific predicate, and durable history/duplicate recovery proves the stable resume message was not already accepted. Older cards and live-only synthetic cards remain historical/non-resumable and never trigger. Current history preserves validated turn status/ID but must be extended from flat text to blocks and a client request identity (`frontend/src/lib/assistant/aevatar-transport.ts:233-241`, `frontend/src/lib/assistant/aevatar-transport.ts:348-401`).

### Draft v8 conflicts resolved in favor of the hard constraints

- Draft v8 requires `card_action: connection_key_attached` so Aevatar learns a `key_id` (`nyx-chat-prd.md:215-228`, `nyx-chat-prd.md:302-306`). Hard constraints 2-3 say Aevatar already reads `/api/v1/keys` and all connect actions are FE -> NyxID, so omit this client block entirely.
- Draft v8 discovers services through `GET /api/v1/proxy/services` and polls a new `/keys/{key_id}/status` after attachment (`nyx-chat-prd.md:266-277`). The hard constraint says Aevatar already uses `GET /api/v1/keys`; do not add those calls for this feature.
- Draft v8 says detail history alone contains final/current card state (`nyx-chat-prd.md:101-117`). Under the no-key-attachment constraint, the smallest FE contract overlays typed history with NyxID's current keys/catalog reads; Aevatar can update its persisted card when the resume message causes its next `/keys` read, but the FE must not send a state signal.
- Draft v8's no-create/no-delete, client-minted conversation model is compatible with the hard constraint and exposes defects in the current transport (`nyx-chat-prd.md:64-78`).

## 6. Defects Found

### Hard-constraint 1 violations

- **Aevatar conversation create:** `createConversation` issues `POST /assistant/conversations`, which is neither sending a chat message nor reading history (`frontend/src/lib/assistant/aevatar-transport.ts:633-637`). The empty-state send path calls it before every first message (`frontend/src/hooks/use-assistant.ts:311-347`). Replace it with a client-minted conversation UUID/lazy first send.
- **Aevatar conversation delete:** `deleteConversation` issues `DELETE /assistant/conversations/{id}` (`frontend/src/lib/assistant/aevatar-transport.ts:656-670`), and the page exposes it through the sidebar flow (`frontend/src/pages/assistant.tsx:66-83`, `frontend/src/pages/assistant.tsx:119-122`). Remove/hide this v1 action; local deletion alone would be misleading because history would return.
- **Aevatar approve endpoint:** `decideApproval` posts to `/assistant/conversations/{id}/approve` and consumes another SSE continuation (`frontend/src/lib/assistant/aevatar-transport.ts:792-854`, `frontend/src/lib/assistant/aevatar-transport.ts:933-951`). The hook and page route in-chat approval through that method (`frontend/src/hooks/use-assistant.ts:400-421`, `frontend/src/pages/assistant.tsx:155-157`). Approval actions must call NyxID's own approval API only; this is unrelated to connect implementation but cannot be preserved.
- **The abstraction codifies the violations:** `AssistantTransport` requires remote create/delete/decide operations and documents the Aevatar approve endpoint (`frontend/src/types/assistant.ts:222-250`). Narrow the production transport so only history reads and chat send+stream can reach Aevatar.

The existing `POST /assistant/conversations/{id}/stream` is a single message-send request whose response body is the SSE (`frontend/src/lib/assistant/aevatar-transport.ts:1100-1166`), so it satisfies the hard constraint's "sending a chat message (with its stream)" purpose even though its path differs from Draft v8's strawman `/messages` path (`nyx-chat-prd.md:64-72`). Do not add a separate stream/attach endpoint.

### Other material gaps

- **Cards vanish on true reload:** current Aevatar history entries are flat strings and the FE always projects them to text, while connect cards exist only in the in-memory event mirror (`frontend/src/lib/assistant/aevatar-transport.ts:233-241`, `frontend/src/lib/assistant/aevatar-transport.ts:382-401`, `frontend/src/lib/assistant/aevatar-transport.ts:1967-2037`).
- **No automatic continuation:** the card explicitly says "send your request again," has no completion callback, and the page has no connect handler (`frontend/src/components/assistant/blocks/connect-card.tsx:68-75`, `frontend/src/pages/assistant.tsx:145-158`).
- **OAuth leaves the transcript:** `OAuthStep` hard-redirects the main window and sets `/keys/{id}` as the callback path (`frontend/src/components/dashboard/add-key-dialog.tsx:1454-1469`).
- **Device completion may not repaint the card promptly:** device polling invalidates provider and LLM queries but not the keys query consumed by `ConnectCard` (`frontend/src/hooks/use-providers.ts:217-239`, `frontend/src/components/assistant/blocks/connect-card.tsx:37-65`).
- **A fake auth kind reaches rendering:** live blocker conversion hard-codes `api_key` because the event lacks catalog metadata (`frontend/src/lib/assistant/aevatar-transport.ts:2011-2015`). It is safe only because `AddKeyDialog` reselects by slug; the card itself must not use it to choose an endpoint.
- **Structured blocks are trusted after only a shallow type check:** `ChatThread` casts any object with a `type` field to `ContentBlock` and passes it into typed components (`frontend/src/components/assistant/chat-thread.tsx:42-68`). Typed history/SSE adoption requires transport-boundary runtime validation and bounded payloads; malformed input should reach the existing unsupported shell (`frontend/src/components/assistant/chat-thread.tsx:12-18`).
- **Current block lifecycle is internally inconsistent:** a blocked connect card remains `needs_connection`, yet `finalizeActivity` emits `block.completed` for it without making it terminal (`frontend/src/lib/assistant/aevatar-transport.ts:2213-2217`, `frontend/src/lib/assistant/aevatar-transport.ts:2270-2287`). Treat the card as an actionable persisted gate, not a completed terminal block, or define a separate "turn blocked, card open" lifecycle in the Aevatar contract.

## 7. Open Questions

1. **Will Aevatar emit/persist the full `connect_card`, or only persist its current blocker signal?** Recommended default: full existing block in typed assistant `blocks`, including exact `key_id` for unauthorized, with the current custom event accepted by the FE for one live-only compatibility release. This gives stream/history parity and avoids a second public signal vocabulary (`frontend/src/types/assistant.ts:34-57`, `frontend/src/lib/assistant/aevatar-transport.ts:1593-1596`). The Aevatar source repository was not supplied, so its owner must confirm the producer/storage file and rollout date.

2. **Who owns continuation: FE resend or a long-lived Aevatar waiting turn?** Recommended default: FE resends the original text through the ordinary chat POST, using the durable idempotency contract in question 7 when available. It matches Ean's proven behavior and the current target's terminal `blocked` turn (`public/app.js:710-727`, `frontend/src/lib/assistant/aevatar-transport.ts:2171-2182`) without adding an Aevatar signal/polling endpoint. A later Aevatar-owned wait can replace it without changing the card/action contract.

3. **Should automatic resume create a visible repeated user message?** Recommended default: yes. It is honest transcript history and lets the normal message/stream path do all work. Label it locally as a resumed request only if product wants distinct styling; do not append hidden catalog or connection context to the text. The target currently represents every send as a normal user text block (`frontend/src/lib/assistant/aevatar-transport.ts:729-750`).

4. **OAuth popup versus full-page redirect?** Recommended default: popup with NyxID key polling, preserving the main transcript; retain a user-clickable full-page fallback only when the popup is blocked. The current whole-tab redirect is the one modality that cannot complete "right there" (`frontend/src/components/dashboard/add-key-dialog.tsx:1454-1469`).

5. **What should an unknown/removed catalog slug do?** Recommended default: render the assistant reason in a disabled card with a link to AI Services; never show a generic credential input and never trust Aevatar-supplied provider IDs/URLs. The current dialog already no-ops a missing prefill and falls back to its catalog picker (`frontend/src/components/dashboard/add-key-dialog.tsx:2364-2405`).

6. **Should chat users see the normal post-connect Agent Key onboarding?** Recommended default: no. Assistant mode should call `onConnected` and close as soon as the NyxID service key is active; the existing verify step is designed to mint a separate Agent Key for external AI tools (`frontend/src/components/dashboard/connect-verify-step.tsx:65-88`, `frontend/src/components/dashboard/connect-verify-step.tsx:97-119`), which is not required for Aevatar's already-configured identity.

7. **Can Aevatar durably deduplicate a caller-supplied resume ID across reload?** Recommended default: require it before promising reload-safe automatic resume, and return the accepted client ID in history; a defined duplicate/already-accepted response is an acceptable alternative. The current transport generates a new ID internally and history contains no client request ID (`frontend/src/lib/assistant/aevatar-transport.ts:233-241`, `frontend/src/lib/assistant/aevatar-transport.ts:1040-1049`). Until Aevatar supplies this, use best-effort live auto-resend plus a visible manual retry, not an exactly-once claim.

8. **Can Aevatar identify the exact failed key for `NYXID_UNAUTHORIZED`?** Recommended default: require `key_id` on that reason code because another active key with the same slug does not prove the failed authorization was repaired; the current card already keeps unauthorized separate from same-slug connected state (`frontend/src/components/assistant/blocks/connect-card.tsx:38-65`). If Aevatar cannot supply it, scope v1 automatic completion/resume to `NYXID_SERVICE_NOT_CONNECTED` and leave unauthorized cards on manage/manual retry.
