# Issues #1850–#1854: validity, root causes and plan

Status: **approved by GPT-6-Astra in round 5** (revision 5; rounds 1–4 raised
16, 8, 7 and 1 findings, all resolved or justified; dispositions at the end). Implementer: GPT-6.1-Sol (heca, xhigh, full access).
Reviewer: Opus (author of this plan).

All five reports come from one NyxBot session (Telegram group support bot with
a knowledge pack). Each was checked against `main` at `e3c1024f`.

## Summary

| Issue | Verdict | Root cause (proven) |
| --- | --- | --- |
| #1850 Telegram setup leaves the chat | **Valid, bug** | `TelegramNewConnect` rewrites the URL to `/channel-bots?connect=telegram-new` with `replace: true` even inside the in-chat setup dialog (`stayInPlace`), replacing the chat route and its history entry. |
| #1851 Reply stops mid-sentence | **Valid, bug + UX gap** | The NyxAgent relay withholds the last `max(raw_key.len(), marker.len())` bytes (≈64–73 B, ≈25 CJK chars) of streamed text until the next delta; during tool calls no delta arrives. Once any text exists the UI shows no running indicator other than the caret. |
| #1852 Red ✕ while the turn continues | **Valid, UX bug** | `ActivityBlock` shows ✕ whenever any step failed and no step is running at that instant, regardless of turn state; rows show no failure state or reason; the list is capped at 40 so "40 actions" can understate; activity writes are not fenced to the turn. |
| #1853 Ornn rejects the package; user must Deny/Discard | **Valid, bug** | NyxID validators accept packages Ornn forbids (root entries other than `SKILL.md`/`references/`/`assets/`/`scripts/`, `<`/`>` in frontmatter, "claude"/"anthropic" in the name). Ornn's `/skill-format/validate` runs only after owner approval, its `violations` are discarded, and nothing wakes NyxBot after the card outcome. |
| #1854 Uploaded document lost after a context reset | **Valid, bug** | `bounded_recap` keeps only the newest 20 messages (8 KiB, newest first) and never lists earlier attachment IDs, so NyxBot cannot call `nyx__attachment_read` for earlier uploads and the original goal can fall out. Nothing tells the owner, at review time, which uploaded documents were actually read. |

## Design principles

- Fix at the owning layer: streaming redaction in the relay; Ornn wire-format
  knowledge in the Ornn adapter (`assistant_learning_publication.rs`, per
  `docs/AGENT_SKILLS.md` "Adapter boundary"); recap in the engine;
  presentation in the frontend. `handlers → services → models` only.
- One source of truth per rule; facts, never synthetic progress (FI-006); step
  failure ≠ turn failure; no invented correlation IDs.
- Privacy contracts unchanged or tightened: activity metadata is identifiers
  plus fixed vocabularies and numeric status; Ornn `message` text, response
  bodies, ZIP entries and skill contents never leave the adapter.
- Durable cross-turn facts live in MongoDB (FI-004); multi-document effects
  commit in one transaction.
- Additive serde-defaulted fields, no env vars, no error codes; replace, don't
  keep, the old hold-back and colour-only summary (FI-007).

## Plan

### #1850 — keep the chat, return to it

1. `ChannelBotConnectProps` gains `stayInPlace?: boolean`, passed from
   `ChannelBotSetup`. `TelegramNewConnect` with `stayInPlace` keeps the request
   ID in component state and never navigates; on remount it resumes the
   actor's current request (`GET /channel-bots/telegram-new` without
   `request_id` returns `current`). Full-page and `/channel-bots` behaviour is
   unchanged.
2. In place, completion reads "@bot is connected. NyxBot will continue in
   this chat." with primary **Back to chat** (closes the dialog); "You can close
   this page" becomes "You can close this dialog". Cancel/expiry/failure keep
   their truthful copy. Closing reveals the untouched chat; the composer draft
   survives because the route never changes.
3. Full-page return (new tab or channel origin): `setup_link_tool` loads the
   owner-scoped source conversation and appends one query parameter
   `return_to` whose value is an **ID**, not a URL: the conversation ID
   (`nyxa-` + 32 hex) or, when the row has `group_id`, the group ID (`nyxg-` +
   32 hex, validated with the shared group-ID validator). Stale/missing
   source → no parameter. Serialized with `url::form_urlencoded`. The client
   reads the **raw** `window.location.search` once on mount, before
   `channelBotSetupRewrite`/`parseChannelBotSetupPageSearch` normalization
   (which collapses duplicates and JSON-quotes values): `return_to` must
   appear exactly once, non-empty, and fully match `^nyxa-[0-9a-f]{32}$` or
   `^nyxg-[0-9a-f]{32}$`; otherwise it is ignored. The validated canonical ID
   is then carried through every `TelegramNewConnect.updateSearch` replacement
   (initial sync, request start/resume, cancel) so refresh keeps it. **Back to
   chat** calls the router with
   `{to: "/assistant", search: {c}}` or `{g}` — no URL is ever parsed or
   assigned, so there is no redirect surface. The assistant page's
   owner-scoped loading remains the permission check (another account or a
   deleted group shows its existing not-found state). Shown on success,
   cancel, expiry and error. The in-chat modal ignores the parameter
   (`SAFE_SETUP_QUERY_KEYS` unchanged).
4. Tests: in-place flow never navigates or changes `location`; remount resumes
   the current request; return-target parser rejects duplicates, empty,
   uppercase/short IDs, URLs, `//host`, encoded values, extra junk, and both
   kinds at once; mounted-router tests that the target survives initial sync,
   request-ID insertion, cancellation, completion and refresh for both
   conversation and group targets; backend tests for an ordinary thread, a hidden group-member
   thread and a missing row; the existing watch wake test passes for
   `telegram-new` auto-connect.

### #1851 — no withheld text, visible running state

1. Relay hold: replace the fixed hold-back with the minimal safe hold, a pure
   function returning the longest suffix of the redacted accumulated text that
   is a *proper prefix* of any live secret (raw thread key, context marker),
   char-boundary aligned. Invariants (documented in code and
   `08-nyxagent-engine.md`):
   - (a) Within one upstream response the emitted bytes are a prefix of that
     response's redacted accumulated delta text.
   - (b) The unemitted tail is exactly the longest suffix that is a proper
     prefix of a live secret; any secret occurrence not yet complete starts
     inside it; complete occurrences are already replaced.
   - (c) Continuation boundary: today the held tail is flushed and `"\n\n"`
     appended (`completed = partial + "\n\n"`), identical to the persisted
     text. A secret cannot be contiguous across that separator in either the
     emitted stream or the persisted text, so the boundary flush exposes
     nothing a redactor could match. Kept, with a regression test.
   - (d) Error/timeout/cancel paths emit no further `block.delta` from the
     hold (unchanged); the authoritative `block.completed` text emitted by
     `complete_turn` is unchanged and already redacted.
   Tests: CJK/ASCII emit fully with no secret prefix; key and marker split
   across 2–3 deltas never appear contiguously in the concatenated emitted
   stream; near-miss prefixes release on the next delta; key/marker split at a
   tool-budget and at a turn-timeout continuation boundary never appear
   contiguously; char boundaries; empty secrets ignored.
2. Turn status model (frontend, one module used by #1851 and #1852). Phases,
   each backed by a fact, in precedence order:
   - `approval` — a pending acknowledgement or proxy approval in this
     conversation (persisted).
   - `tool` — a running activity (persisted): label + elapsed from `started_at`.
   - `retrying` — live-only `turn.notice` with code `retrying`, emitted by the
     relay when it backs off, rebinds or replaces the credential; cleared by
     the next delta/status event. Polled clients never infer it.
   - `continuing` — `continuations > 0` (persisted) / `turn.continuing`.
   - `working` — live stream connected, nothing more specific known.
   - `active` — no live stream but the server reports the turn active
     (reload, another device, event/channel turn): "Working — the reply
     appears when it is ready".
   A separate connection flag `interrupted` is set when this tab's live
   stream failed while the server still reports the turn active; it adds
   "Connection interrupted; checking every few seconds" next to the phase and
   clears when the turn settles or a new live stream starts.
   Rendering: one status row for the whole active turn (replacing the
   `streaming && !content` dots), `role="status"`, `aria-live="polite"`,
   visible text, `motion-safe:` animation only; removed on
   complete/error/stopped. Delete the assistant-chat-page "Continuing task…"
   line (now a phase).
3. Tests: Vitest per phase and precedence, text present with no running tool
   still shows status, interrupt → poll → settle clears, stop/error clear,
   reduced motion; Rust tests for the hold function and the `retrying` notice.

### #1852 — trustworthy action summary

1. Summary state = turn state: active → the status-model phase text plus
   "N actions" (never ✕); complete → ✓ "N actions", plus "· k failed" in
   muted warning text when steps failed (recovered steps stay visible but are
   not the turn state); turn failed → ✕ "Turn failed" (existing error box
   explains); stopped → "Stopped". Icons carry `aria-label`; text always
   present. Copy never suggests resubmitting.
2. Rows: running / succeeded / failed icon with label; failed rows show fixed
   copy for the failure record and "The assistant can continue after a failed
   step." No trace ID: none exists for activities today.
3. Activity labels (tightening an existing gap). The label is only ever a
   name whose provenance NyxID established:
   - Native NyxID tools (`nyx__*`, `nyxid__*`): the outer name is kept only if
     it is in the compiled native tool registry; otherwise `tool`.
   - Service tools and `nyx__call_tool`: the activity starts as the fixed
     label `tool`. When dispatch resolves a published, authorized operation,
     it updates the same activity (via the existing `ACTIVITY_ID` task-local,
     turn-fenced) to that operation's canonical tool name **before** the
     downstream request is sent. Unresolved, refused or unknown names never
     replace `tool`.
   So no caller-supplied text is persisted, polled or copied onto the settled
   message unless it equals a registry or resolved published name. Tests: a
   syntactically plausible unknown name carrying private text, complete
   NyxID/Agent Key/provider-key shapes as outer and nested names, and
   stop/settlement before dispatch returns — none reach active or settled
   DTOs or the UI.
4. Turn fence: `activity_started(…, turn_id)` and `activity_finished(…,
   turn_id, failure)` filter on `active_turn.turn_id` from `ChatAuthority`.
   `activity_started` atomically `$push`es (bounded `$slice`) and `$inc`s
   `active_turn.activity_total` in one update. `activity_total` counts every
   recorded activity of the turn, including machine and evicted ones; it is
   copied onto the settled message. The UI shows the list count and, when
   `activity_total` exceeds the list length, "latest N of M shown".
5. Failure record `failure: {kind, status?}` with fixed `kind`:
   `service_status` (downstream non-2xx; `status` set), `tool_error` (MCP
   `isError` from a NyxID tool), `refused` (JSON-RPC error other than
   −32603, including capacity 429 and invalid input), `internal` (−32603 or a
   non-2xx response without a JSON-RPC body). A `ToolFailure` response
   extension is inserted where the outcome is known (service tool content,
   `rpc_error`, error `tool_result`, concurrency-limited); an error response
   without it maps to `tool_error`.
6. Wiring (all additive, serde/Zod defaults): `models/assistant_conversation.rs`
   `TurnActivity.failure`, `ActiveTurn.activity_total`;
   `models/assistant_message.rs` `activity_total`; handler DTOs
   `ActivityResponse`, `ActiveTurnResponse`, settled message response;
   `schemas/assistant-nyxagent.ts`; `nyxagent-transport.ts` mapping into
   `RuntimeToolCallInfo`/`ChatMessage`; `chat-types.ts`.
7. Mixed versions: settlement (`replace_one`, transactional) and steering
   (`assistant_steering.rs` typed read + `replace_one` during a live turn)
   rewrite the whole conversation, so an old replica can drop the new
   `active_turn` fields. Only display metadata (`failure`,
   `activity_total`) lives there; no state, authority, limit or billing
   depends on it and the UI falls back to the boolean status and list length.
   Every behavioural counter in this plan lives in its own collection that
   legacy writers never touch (#1853.4). New code writes the display fields
   with field-level updates only. Tests: rows without the fields deserialize
   and render; an old-shaped replace removing them leaves the UI correct.
   The persisted `cancelled` message status keeps rendering as "Stopped".
8. Tests: classification per response shape; label sanitization (secret-like
   and arbitrary nested names); old-turn/new-turn race (stale `turn_id` writes
   nothing); count with eviction; Vitest for every summary state including
   "active with an earlier failure" (no ✕) and "completed with recovered
   failures".

### #1853 — catch format errors before the card; never make the user relay them

1. Ornn wire-package contract in the adapter, run **after** each source's own
   validator (authored credential/content diagnostics; L1's stricter
   redaction/provenance checks are unchanged): supporting paths must start
   with `references/` or `assets/` (text drafts never ship `scripts/`; nested
   paths below those stay allowed); no `README.md` anywhere at the package
   root; `name`/`description` contain no `<`/`>`; `name` contains no
   "claude"/"anthropic" (case-insensitive). Authored drafts return caller-safe
   `SkillDraftValidation` rules (`root_entry_not_allowed`,
   `angle_brackets_not_allowed`, `reserved_name_term`) with field paths; L1
   keeps its generic refusal. Tests prove authored URLs/nested reference
   paths still pass and L1 still rejects secret-shaped/private content.
2. Remote preflight before the card (authored): inside
   `approval_binding_typed`, when it first builds the package for an authored
   proposal (the `publication.is_none()` branch), call the read-only Ornn
   validate on those exact bytes before persisting `publication`; `create`
   therefore reaches `acks::request` only for a package Ornn accepted.
   Explicit invalid verdict → `BindingFailure` with the mapped rules; `create`
   removes the just-inserted proposal (existing cleanup) and returns a
   caller-safe validation error. Transport/availability failure → proceed;
   publish-time validation stays authoritative. L1 bindings are unchanged.
3. Strict Ornn rule parser (adapter-private), used for both shapes Ornn
   returns: the 2xx validate verdict (`data.valid`, `data.violations[].rule`)
   and a 4xx problem body on publish (`errors[].code` / `errors[].path`,
   Ornn `docs/ERRORS.md` `validation_error`), parsed inside the bounded body
   read in `handlers/agent_skills.rs` and carried on the classified outcome as
   a fixed-enum summary (`OrnnOutcome::Response` gains an optional bounded
   rule list; nothing else). `OrnnCode` maps the documented root codes
   `validation_failed` and `frontmatter_validation_failed` to
   `ValidationFailed` (other unknown codes stay `Unknown` → uncertain). The
   rule summary flows through `PublishOutcome::Refused { rules }`,
   `DeferredFailure`, persisted `failure_rules`, preview and the terminal
   event. Adapter-to-publication test: the documented 400 `errors[]`
   envelope yields a definitive validation refusal, safe rules and one repair
   notification. Exact IDs map to enum members
   (`allowed-root-items`, `no-readme-md`, `skill-md-exists`,
   `no-xml-brackets`, `description-no-xml`, `name-matches-folder`,
   `name-no-forbidden-terms`, `unexpected-error`); `frontmatter.<path>` maps
   only for a fixed set of known fields (`name`, `description`, `version`,
   `metadata.category`, `metadata.output-type`, `metadata.runtime`,
   `metadata.tool-list`, `metadata.tag`, `metadata.runtime-env-var`,
   `metadata.depends-on`; numeric indices stripped); any other value — never
   echoed — increments `other`. Malformed or absent details → explicit
   "details unavailable" copy. `message`, `title`, `detail`, other fields, raw
   bodies and ZIP entries never reach `AppError`, audit, logs, previews,
   cards, events or responses; at most 10 rules kept. Negative tests put
   sentinel secrets in rule values, messages, titles and nested fields for
   both the 2xx verdict and a 400/422 publish refusal.
4. Bounded repair, no user relaying:
   - In-turn: the draft tool's validation error is an MCP `isError` result
     the model can act on in the same turn; no card exists until the package
     validates. The cap lives in a new collection
     `assistant_skill_draft_attempts` (UUID-v5 `_id` from conversation and
     turn, `user_id`, `conversation_id`, `turn_id`, `rejections`,
     `created_at` with a 24-hour TTL index, `COLLECTION_NAME`), which no
     legacy writer touches. A format rejection does one atomic
     `find_one_and_update` `$inc` with upsert returning the new value; the
     draft call checks the current value first and refuses at ≥3 with "report
     the remaining rules to the owner". Concurrent calls cannot exceed the
     cap by more than the calls already in flight, and none of them raises a
     card. Tests: old-shaped conversation replace mid-turn leaves the count;
     concurrent rejected drafts; cap message.
   - Deterministic auto-rewrite is **not** applied: every known violation
     needs a semantic edit (moving a file breaks references inside SKILL.md;
     removing brackets changes authored text). NyxBot holds the context to
     make the edit and the owner always reviews the exact final bytes.
   - After approval (rule drift, unknown rules): `validate` returns
     `Validation { status, rules }`; the failure record stores
     `failure_rules` next to `failure_code`; owner preview and
     `learning_list_proposals` expose fixed per-rule copy. For
     `requires_new_package` codes the card says NyxBot was asked for a
     corrected draft (no "Deny or discard…" instruction).
5. Durable, exactly-once chat notification: when an authored publication
   reaches `pinned` or a `requires_new_package` failure, the same MongoDB
   transaction that records that terminal state — and only when that fenced
   transition matched (`matched_count == 1`) — also `$push`es a
   `skill_publication` `AgentEvent` (UUID-v5 ID from proposal ID, revision and
   transition; push guarded by `pending_events.id` ≠ ID) to the card's
   conversation. Wake after commit; the existing deferred-wake retry
   (`assistant_team_service::queued`) is the backstop. Where the terminal write
   is not yet transactional it becomes one transaction with the push. Event
   text: identifiers, name, version, code, rule copy; success says
   "published and attached; not yet tested". Event-turn guards (3-turn streak,
   hourly cap) bound automatic repair, and the event tells NyxBot to report to
   the owner if a corrected draft is rejected again. Frontend event label for
   the new kind.
6. Tests: contract (root files, nested reference paths, README, brackets,
   reserved terms) for both validators; authored create with Ornn violations →
   no card, proposal removed, mapped rules; Ornn unavailable → card raised;
   third rejection in a turn → cap message; publish-time violation →
   `failure_rules` + one event; crash after commit (transaction commits event
   with state) and concurrent settlement → one event; pinned → one event;
   copy tests.

### #1854 — survive a context reset with sources, goal and scope intact

1. Recap = owner requirements + tail + manifest, ≤12 KiB with fixed
   sub-budgets (owner ≈5 KiB, tail ≈5 KiB, manifest ≈2 KiB):
   - Owner requirements of record: only messages with server-established
     owner provenance. New additive `AssistantMessage.author`
     (`"owner"`/`"guest"`), set at admission from the turn's server-derived
     `guest` flag for `user`-role messages. Eligible: `author == "owner"`, or
     legacy rows with `origin == User` (app messages are always the owner's).
     Legacy channel rows without `author`, guest messages and `group` /
     `event` / `orchestrator` roles never enter this section. One bounded
     query: the newest 40 eligible messages plus the earliest eligible one,
     with the tail's filters (no execution-pending, current turn excluded).
     Rendered oldest first, each ≤1,000 bytes with "[truncated]", skipping
     ones already in the tail. Guest turns get no owner section. Group-member
     threads therefore rely on the tail (no group-collection reads).
   - Tail: newest messages as today, with "[truncated]" and "[N earlier
     messages omitted]" markers; `author == "guest"` lines are labelled
     "user (guest)" so a guest's words are never mistaken for the owner's.
   - Manifest: message-bound uploads of **this conversation only**
     (`assistant_messages.attachments`, `origin == "user_upload"`), newest
     first, up to the budget, fields id/safe name/type/size/pages, expired
     marked via the existing retention check, untrusted-data wording, the
     `nyx__attachment_read` hint and, when truncated, "[N older uploads; list
     them with nyx__attachment_list]". Guest turns get none.
   - Voice keeps its current recap call.
2. `nyx__attachment_list {cursor?, limit≤50}`: paged metadata (id, safe name,
   type, size, pages, expired, bound time) of this conversation's
   message-bound user uploads, newest first, opaque cursor. The fully
   serialized MCP result (rows, cursor and hint) stays under 9,000
   characters: fewer rows than requested are returned when needed, and the
   cursor is derived from the last row actually included, so no row is
   skipped (same bounded-result pattern as `mcp_transport.rs` image notes). Same authority as
   `nyx__attachment_read` (the active thread's assistant credential and
   conversation fence); refused for guest turns; no content, no other
   conversation or group.
3. Paged reads mark incompleteness and fit the wire: `nyx__attachment_read`
   and `skill_read` add `complete: false` and a fixed continuation hint
   whenever `next_offset` is present. `skill_read` already budgets the
   escaped MCP envelope (`agent_skill_service::page`, ≤9,200 bytes); the new
   fields go inside that budgeted value. `nyx__attachment_read` currently
   budgets only its inner JSON; it adopts the same rule and budgets the
   **final MCP result** (page JSON serialized into the text content, wrapped
   and escaped again by `tool_result`) below 9,000 characters. Page text
   is reduced until the final envelope fits; `next_offset`, `complete` and
   the recorded coverage interval are derived from that final page only.
   Regression tests with quote-, backslash- and control-character-heavy text
   serialize the actual MCP envelope, follow every `next_offset` to
   reconstruct the original exactly, and assert coverage never includes
   characters dropped to meet the budget.
4. Read coverage (an observation, labelled as such): each
   `nyx__attachment_read` atomically `$push`es `{start, end, at}` for the
   character range actually returned (after the serialization-budget
   reduction) with `$slice` −512, and `$inc`s `reads`, filtered by attachment,
   owner and conversation. `$push` is atomic and commutative across
   concurrent/out-of-order reads; union is computed at display time, so
   adjacent sub-unit or unaligned pages combine exactly and unread gaps are
   never filled. If `reads` exceeds the retained intervals, coverage is shown
   as a lower bound ("at least N%"). "Not read" appears only when `reads ==
   0`. The union of intervals with `at` after the conversation's latest
   `context_reset_at` is shown separately ("since the last context reset"),
   so a full pre-reset read plus a one-page reread is not presented as a full
   recovery.
5. Explicit scope declaration and distinct consent:
   - `draft_agent_skill` requires `scope: {status: "complete" | "reduced",
     omissions: [...]}`; `reduced` needs 1–8 omissions (each ≤200
     characters, validated by the authored text rules), `complete` none.
     Stored encrypted on the proposal row as a separate additive field (not in
     the package or its body, so old body decoders are unaffected). The
     canonical scope is part of the authored-request fingerprint (identical
     bytes with a different declaration are a different proposal) and of
     `publication::binding` **only when present**, so scope-less legacy rows
     keep byte-identical bindings and live cards. Owner edits keep the
     declaration but bump the revision; acceptance is stored with the exact
     revision and approval digest and is reused only to resume that same
     operation, so any edit voids it. Legacy pending proposals without scope
     show "Scope not declared (drafted before this release)" and keep their
     existing behaviour.
   - The review card shows the declaration and, separately labelled as
     observations, this conversation's uploads with coverage ("read
     completely" / "read N%" / "at least N%" / "not read" / "expired") and,
     when a reset happened, the since-reset coverage. For `reduced`, Allow stays disabled until the owner
     ticks "I accept this reduced scope", and the decision carries
     `accept_reduced_scope: true` (additive request field); the server refuses
     a reduced-scope publication without it and records metadata-only
     acceptance (counts, no text) in the publication and audit.
   - The server cannot verify a "complete" claim semantically; the coverage
     observations make a contradiction visible at the consent point.
   - Tool description: read sources to completion; declare every omission,
     including material that exceeds the draft limits; never present a
     reduced package as complete.
6. Tests: greeting-first thread with mid-history rules, >20 messages, reset →
   rules and ordering in the recap; budget with CJK; guest unchanged; expired
   marked; >budget uploads → list hint and `nyx__attachment_list` pages to
   the oldest upload; list/read ACL (other owner, conversation, guest);
   paged-read flags; concurrent disjoint/overlapping reads, out-of-order
   completion and budget-reduced pages; a fully read attachment omitted from
   a `complete` draft shows its coverage on the card; `reduced` draft cannot
   publish without acceptance and can with it; scope validation.

## Out of scope

- Raising the 7,500-character authored draft cap (product decision; the scope
  declaration makes any shortfall explicit and consented).
- A server-inferred "required sources" ledger: the server cannot know which
  materials a task needs. The explicit declaration plus observed coverage is
  the verifiable substitute.
- NyxAgent upstream protocol and upload retention changes.

## Rollout

Additive fields and one new collection (`assistant_skill_draft_attempts`, TTL
index); no migrations or env vars. Display-only fields may be dropped by old
replicas' whole-document conversation rewrites (#1852.7); behavioural state
(draft-attempt cap, `failure_rules`, scope, acceptance, `read_units`) lives in
collections/fields old writers never replace. Mixed versions fail
closed for scope: an old replica cannot publish a scope-bearing card because
its recomputed binding lacks the scope digest, so `consume_action_in_session`
refuses the card digest; an old replica rejects `scope` in draft input
(`deny_unknown_fields`) and `accept_reduced_scope` in the decision body, both
safe refusals the caller can retry. Rollback is equally fail-closed. To avoid
user-visible refusals during the deploy window, operators may keep
`assistant:agent-learning` off for affected people until every replica runs the
release (documented in `docs/AGENT_LEARNING.md`). Tests: legacy row binding
unchanged; scope-bearing binding differs; old-shaped binding refuses a
scope-bearing card. Docs:
`docs/chat/08-nyxagent-engine.md`, `docs/chat/10-uploads.md`,
`docs/AGENT_SKILLS.md`, `docs/AGENT_LEARNING.md`, `docs/CHANNEL_BOT_RELAY.md`.
