## Backend design

### A. Bounded safe Telegram diagnostics

Add an internal typed diagnostic result in `telegram_new_api.rs`, retaining `call` as a compatible AppResult wrapper for all existing callers. A detailed call variant used by prompt delivery returns safe metadata only: failure class (`network`, `timeout`, `http_rejected`, `provider_rejected`, `invalid_response`, `response_too_large`), HTTP status when available, numeric Telegram error code when valid, and a small closed reason taxonomy (`rate_limited`, `unauthorized`, `forbidden`, `bad_request`, `provider_unavailable`, `unknown`). Optional retry-after is numeric and bounded, not an instruction to retry automatically.

Keep the current 20-second request timeout and streamed 1 MiB limit, including error bodies. Disable redirects for credential-bearing Telegram requests through the appropriate dedicated client, while preserving the WireMock injection seam; never forward the token to a Location target. Parse only bounded envelopes; no raw description is stored, returned or logged. Derive reasons from status/error code or exact known matches, never arbitrary description truncation. `ok=true` still requires a valid result for prompt send confirmation: a usable message ID establishes Bot API acceptance. Malformed success, body interruption and timeout are uncertain, not confirmed failure/no-send. Do not expose reqwest errors containing the credential URL. Preserve token acquisition in Zeroizing memory and all existing error codes.

### B. Prompt-delivery state without changing creation authorization

Add one optional/defaulted nested `prompt_delivery` record to `TelegramBotRequest`; old rows deserialize as no observation. Fields: attempt UUID, triggering update ID (and monotonic update boundary), phase (`instructions`/`keyboard`), outcome (`sending`/`accepted`/`rejected`/`unknown`), attempted/completed BSON dates, and the bounded safe diagnostic fields above. Do not add a new top-level `TelegramRequestStatus`: the existing creation lifecycle remains authoritative. `accepted` describes keyboard delivery only; instruction success by itself cannot set it.

Claim an attempt with the exact request ID, actor/owner, manager observation, bound sender, active `waiting_bot` state and unexpired deadline before sending. Use a separate attempt identity/CAS for outcome updates so prompt observability does not advance creation revision or invalidate a legitimate concurrent creation. Completed/expired/revoked requests win over late prompt results. A stopped process leaves `sending`, which the DTO projects as unconfirmed after a bounded timeout (at least the two call budgets); no automatic replay of the keyboard is triggered by that state.

Retain the existing webhook contract: first-message delivery failure can return retryable failure; once instructions were accepted, keyboard failure is acknowledged and recorded. DB outcome-write failure after provider dispatch must not cause the keyboard to be replayed blindly: retain the durable in-flight attempt, log only safe IDs/class, and acknowledge. Duplicate updates whose keyboard dispatch is already recorded as started/settled must not send another keyboard; a fresh `/start` update may create a new attempt after live checks. A duplicate prior first-send rejection may follow existing retry semantics. Persist a monotonic per-request update boundary so an older completed update cannot resend after a newer attempt replaces its snapshot. Serialize overlapping attempts with a bounded durable claim: a fresh command must not replace an in-flight attempt until its dispatch horizon expires. A timed-out attempt remains unknown; only a new explicit command may retry. Recheck live request authority before the keyboard dispatch, and never mark a prior attempt accepted from a later response. Tests must use distinct update IDs for distinct commands and the same ID for actual redelivery. Do not serialize durable payloads. Unbound Telegram-first `/start` keeps current claim flow and receives safe logging but no invented account-bound request record.

The private `/start` retry must re-read the live request, enforce expiry and owner access, preserve `start_update_id`, and refuse to turn ready/provisioning/connected/suspended/expired/cancelled requests back into waiting. Manager configuration/observation changes invalidate recovery. Observe existing setup-authority fences for platform installations; do not let the new fallback bypass those. No generic delivery retry worker is introduced.

### C. Recovery link and authority

Implement human-only, actor-rate-limited `POST /channel-bots/telegram-new/requests/{id}/creation-link`. Use the existing human check, five-per-minute mutation limiter and no-store/no-referrer response headers. Empty body; accept no destination, manager, bot token, assistant ID, conversation ID or redirect URL. Return a dedicated `{request, creation_url}` DTO.

Eligibility is active, unexpired, auto-connect website request in `waiting_bot`, bound private sender and start update, no observed child/bot, current manager ready and matching observation, and live initiating-person/destination authority. Legacy consent and Telegram-first claimed requests keep their current paths. Platform-installation `setup_authority` requests are explicitly ineligible for this new browser recovery endpoint and instruction recovery anchor. Preserve their existing provisioning path and authority fences, and test that this work adds no bypass. Extending this recovery to installations would require a separate Astra plan assessment.

Persist an optional tagged `creation_context` on new website requests: an explicit `standalone` marker, or `hosted` with the exact link ID/creation identity (including its saved creator user ID) and an optional exact watch snapshot. Absence is legacy/unknown, never evidence of standalone origin; legacy absent-context rows are ineligible for this new recovery endpoint and anchor while their existing handoff/creation paths remain supported. Capture the hosted snapshot in the same `insert_telegram_request` transaction that associates the exact link and inserts the request. Snapshot only required bounded nonsecret provenance: watch ID, owner/kind/platform, agent ID, source conversation ID, created/expires timestamps, invocation ID, report target and report-provenance version. Store no chat text, tokens, callback destinations or provider payloads. Use BSON date helpers. If a watch was present, deletion/replacement/retargeting or changed provenance refuses recovery; never downgrade to no-watch/standalone. A previously absent watch must not silently adopt a later target. No shared watch/assistant model contract changes are needed; source conversation checks must preserve supported hidden group-member sources. The exact saved context, rather than a newly inferred context, must be used by both endpoint and instruction-anchor eligibility. Return the persisted snapshot consistently after transactional insertion.

For hosted requests, revalidate the exact still-pending link and its saved creator/owner/platform/request association. Keep the link creator separate from the Telegram request initiator: existing organization links may be created by one admin and first started by another live authorized admin. Snapshot the actual link creator in the hosted context and compare the link against that value; never require created_by_user_id to equal request.actor_user_id. The request remains pinned to its initiating person after start, and live owner/admin fences apply to that person. Legacy absence of the entire creation_context remains supported as before; unreleased intermediate context fixtures must be updated rather than guessing a missing creator. Test admin A creating an org link, admin B starting/prompting/recovering/consuming, denial for a third actor resuming B's request, and loss of B's membership. If an assistant watch is attached, retain its exact agent/source conversation/provenance and check that its intended agent and source remain live and owner-authorized; do not discover a different watch by platform, label or newest bot. Bind issuance to an exact observed request generation with a real conditional metadata write in a transaction shared with lifecycle writes (a MongoDB no-op is not a conflict fence), and recheck expiry there. A race with creation or revocation returns the current safe state/conflict, not a newly authorized setup. Responses do not mutate watch bindings or grant authority.

Build the URL exclusively from validated saved manager username and saved label/username suggestion using a URL builder and encoded path/query values. An ordinary instruction-message anchor uses the same builder and eligibility logic after handoff. Do not put the private start challenge or any credential in this URL. Repeat requests return the same native-form destination while still eligible; they do not create bots, rotate challenges, reset expiry or advance the creation boundary. Once the browser observes ready/provisioning/connected it discards cached recovery URLs.

**Trust limitation:** Telegram's form link is not a revocable NyxID capability and carries no request ID. NyxID still admits only a fresh verified `managed_bot_created` from the already-bound private sender, after the handoff update, within the request/observation window, with unchanged provenance and management checks. Never accept `managed_bot` alone, username lookup, `/recover`, or a claimed browser completion as proof. Remote user-created extra bots are possible if a person deliberately submits multiple Telegram forms; NyxID must consume at most one per request and must not automatically provision extras. This is the same provider limitation as opening multiple keyboard forms, not an exactly-once remote-create claim. Late/replayed events cannot revive a terminal request. Actual direct-link event semantics remain a live gate; if Telegram does not deliver the required proof, keep the fallback unavailable and revise this plan under Astra review rather than weaken proof.

For new requests with an explicit creation context, consume the fresh creation event in one transaction: real-write fence the live actor/owner and exact current manager observation, fence the saved standalone/hosted context, then conditionally move the exact waiting_bot request to ready. The request condition includes revision, connection generation (legacy zero matching remains compatible), actor/owner/manager/observation, bound sender/start update, exact creation_context, auto_connect, absent setup_authority and child identity, active state and expiry at consumption. Retain the actual managed_bot_created, private sender, update/date freshness and downstream immutable event/management proof. No link issuance or browser claim substitutes for it. Once this transaction commits, ordinary provisioning owns the next lifecycle stage; do not impose a still-pending hosted-link check after legitimate completion. Leave absent-context legacy and platform-installation paths on their existing authority contracts. A closed/revoked/retargeted context or lost request CAS is intentionally acknowledged without provisioning or fallthrough to a new claim; database/transaction infrastructure failures remain retryable. Await commit/abort and do not hide database failures behind a broad ACK. Test context deletion/retargeting, owner revocation, manager rotation, expiry and concurrent duplicate events at consumption, including one winner and zero second provisioning.
