# Facebook Messenger and Instagram DM channel bots

## Release outcome

A business connects a Facebook Page or an Instagram Professional account to NyxID, selects a support agent, and explicitly opens private chats to customers. A customer sends a text DM from the native app and receives the agent's reply in that same conversation. Each channel can launch when its own Meta permissions and release tests pass.

Build two adapters on NyxID's existing channel relay. Use the platform IDs `messenger` and `instagram`. Ship customer-initiated, one-to-one text conversations. Treat media, story interactions, comments, campaigns, proactive sends and native CMA transport as later product decisions. The pilot uses app-role test accounts and operator-provided credentials. Self-service uses a business administrator's consent in the browser. [Channel relay design](../CHANNEL_BOT_RELAY.md#adding-new-platforms)

## Platform contracts

| Contract | Messenger | Instagram |
|---|---|---|
| Account and login | Facebook Login for a person with the Page's messaging task. Enumerate eligible Pages and require explicit selection. | Instagram Login for Business or Creator accounts. One supported login path gives each connected inbox one identity. |
| Core permissions to validate in the dashboard | `pages_messaging`, `pages_show_list`, `pages_manage_metadata` for Page discovery, messaging and subscriptions. Record any dashboard-required dependency and its use. | `instagram_business_basic`, `instagram_business_manage_messages`. |
| Outbound authority | Page access token for the selected Page. Send to `graph.facebook.com/{version}/{page-id}/messages` with the Page-scoped sender ID and `messaging_type=RESPONSE`. | Instagram user access token for the verified professional account. Send to `graph.instagram.com/{version}/{ig-id}/messages` with the Instagram-scoped sender ID. |
| Inbound identity | Signed `page` event, verified Page ID, recipient equal to that Page for an inbound DM, sender PSID and message `mid`. | Signed `instagram` event, verified professional account ID, matching recipient, sender IGSID and message `mid`. Prove OAuth and webhook IDs refer to the same account using the milestone 1 fixture. |
| Message size | Start with the conservative 2,000 UTF-16-unit budget and confirm the boundary against the pinned API. | Count up to 1,000 UTF-8 bytes per message. Add a UTF-8 unit to `channel_text::TextLimit` and use the existing lossless multipart delivery planner. |

Use separate platform credential descriptors for Messenger and Instagram. The app administrator configures the application credentials and verification token for each. Track the Instagram login client and webhook signing secret separately if the tested setup uses different values. Verify a real signature with the documented secret before accepting a configuration. Existing WhatsApp Embedded Signup configuration and the general Facebook OAuth provider have their own consumers. Give the new channels their own configuration and version pins. ## Implementation contracts

### Receive a customer message

1. Implement both `PlatformAdapter`s and register them in `registered_interfaces`. Share raw-body HMAC verification, the `hub.challenge` handshake, bounded Graph HTTP handling and safe error mapping where the protocols match. Keep credentials, object validation, account identity and Send API requests in their respective adapters. [Adapter registry](../../backend/src/services/channel_adapters/mod.rs) · [Adapter trait](../../backend/src/services/channel_platform.rs)
2. Operators can pilot on isolated test apps using per-bot callbacks. Self-service uses one callback per platform at `/api/v1/webhooks/channel/{platform}/platform` and a subscription for each verified asset. Verify the raw signature before trusting IDs. For a mixed batch, split by asset and admit only matching events to that bot. Include only that event's permitted fields in the agent callback. Scope participant IDs to the platform, asset and bot. Reuse the existing transactional active-identity registration check across owners and enforce it on reactivation. Version or drain the credential binding on app-ID changes since scoped IDs can change. [Webhook dispatch](../../backend/src/handlers/channel_webhooks.rs) · [Bot registration](../../backend/src/services/channel_bot_service.rs)
3. Admit private customer text while the app controls that conversation. Filter self/echo, delivery/read receipts, standby/handover, postbacks, reactions, deletions, stories, group and unsupported events. Honor authoritative provider handover/control signals, including a control change while a reply is pending. Verify the routing behavior on test assets. If a given coexistence mode supplies insufficient evidence, support only verified exclusive routing for that mode at launch and explain that in setup.
4. Opt into atomic inbound admission and reuse the existing metadata-only relay. A duplicate `mid` creates at most one agent turn. Preserve the signed provider event time on admitted inbound metadata. For the pilot and v1, the existing shared dispatcher acknowledges promptly and processes in memory. A successful HTTP acknowledgement confirms receipt only. Process loss before admission or between admission and callback can lose a DM. Count failures, record the last successful callback and test this behavior explicitly. Durable replay would change the relay's storage and delivery contract and has its own scope. [Webhook handler](../../backend/src/handlers/channel_webhooks.rs) · [Atomic admission](../../backend/src/services/channel_admission_service.rs) · [Relay storage contract](../CHANNEL_EVENT_GATEWAY.md#adr-013-pure-passthrough)

### Reply and protect the customer conversation

1. Accept only a message-bound reply to a stored inbound DM. Use the bot's verified asset and the sender from that DM to derive the destination on the server. Apply a conservative 24-hour limit from that qualifying message's signed provider timestamp, also bounded by the ordinary NyxID reply-token lifetime. Missing, future or expired timestamps fail closed. This permits replying to a newer qualifying message when an older reply expires. Extended ad windows and human-agent tags are outside v1. [Meta messaging policy](https://developers.facebook.com/documentation/business-messaging/messenger-platform/policy)
2. Centralize these checks immediately before each Graph send, including each multipart segment. Recheck live bot/owner, binding revision, subscription/control state and reply authority. Refuse a closed window with the existing `ChannelConversationNotReachable` (10011) and a stable reason. Advertise reply-only text. Deny unbound sends in the server paths for `/channel-relay/send`, `nyxid__post_to_chat`, test sends, delayed automation and generic adapter sends. A queued turn must still pass the same check. Use the existing send journal for accepted parts and unknown outcomes. A timeout after dispatch cannot trigger an automatic resend. [Bound reply delivery](../../backend/src/services/channel_reply_delivery.rs) · [Text limits](../../backend/src/services/channel_text.rs)
3. A Page admin or professional account manager owns the inbox. Their customers are external participants. For both adapters, suppress the owner access token on **every** relay callback, including personal and custom-agent routes. Use the signed callback and message-bound reply token. NyxBot verifies an owner only through the existing explicit link-code flow bound to that bot and private sender. A first DM, handle, or match to the Page admin's name confers no authority. Test guest conversation isolation and inability to approve cards or invoke private owner tools. [Inbound callback authority](../../backend/src/services/channel_inbound_service.rs) · [NyxBot receiver](../../backend/src/handlers/nyxbot.rs)
4. Keep the private-chat default at owner-only. For customer support, the wizard asks the operator to select a specialist, confirm guest readiness, and explicitly enable **Everyone** for private DMs. The personal path uses the specialist's guest grants and model readiness. The organization path requires an authorized org admin, a same-org specialist, the existing `nyxbot:org-specialist-channels` rollout/readiness, guest exposure, guest grants and org wallet funding. Surface missing setup and point to the specific setting. Verify guest model/tool charges against the expected payer. [NyxBot access settings](../../backend/src/handlers/nyxbot_chats.rs) · [Organization specialist channels](../CHANNEL_BOT_RELAY.md#bots-linked-to-organization-specialists)

### Connect, reconnect and remove an account

Build on the managed onboarding hooks. Use the owner-bound OAuth connection pattern for Instagram, with its actual short-to-long token exchange and long-lived-token refresh protocol. Schedule refresh while eligible and before expiry, serialize refreshes and recheck current binding before using the result. A revoked or expired grant moves the bot to a visible reconnect state. Facebook needs a Page picker and server-side access to the selected Page token. Store the encrypted per-Page token with its grant provenance, revalidate Page authority on reconnect, and handle loss of the admin's Page task. Disconnecting one Page must preserve sibling installations sharing a login. [Channel credential resolution](../../backend/src/services/channel_credentials.rs) · [Managed flow registry](../../frontend/src/components/channels/managed-flows.ts)

Bind a short-lived, single-use OAuth state to the signed-in actor, requested owner or org, channel and redirect URI. Use the project's PKCE pattern where supported. Validate the live actor and selected asset on completion. OAuth callback retries, double-clicks and concurrent claims must result in one active installation. Track incomplete subscription setup, retry idempotently and expose **Verify** and **Reconnect**. A transfer must reauthorize the destination owner before any new delivery. On disconnect, disable local dispatch and sends first, then reconcile only that asset's subscription and credentials. Process verified provider deauthorization and data-deletion requests using current grant provenance and the project's erasure flow. Exclude credentials, raw bodies and customer text from relay history, logs, diagnostics and review fixtures. [Managed subscription lifecycle](../../backend/src/services/channel_connection_webhook_service.rs) · [Relay health](../CHANNEL_BOT_RELAY.md#x-channel-workflow-health-and-recovery)

### Expose the feature and roll it back

Add independent, default-off enrollment flags for the two channels. Evaluate the acting person in discovery, direct registration, managed start/completion, setup links and NyxBot onboarding. Protect the underlying API even if a client already knows the URL. Teach the catalog, onboarding schema and stored progress, standalone form, CLI and status display the new platform IDs. Show provider consent, verified account name, webhook health, guest readiness and a native-inbox test as separate steps. Enable a pilot cohort after every serving replica understands the adapters. Keep both on NyxID's relay. [Platform catalog](../../backend/src/services/channel_platform_catalog_service.rs) · [NyxBot onboarding schema](../../frontend/src/schemas/nyxbot-onboarding.ts) · [Current channel chooser](../../frontend/src/features/nyxbot-onboarding/channel-step.tsx)

Turning off enrollment blocks new connections and preserves management/disconnect for existing customers. For a delivery incident, suspend affected bots or the affected platform's dispatch and egress, including in-flight replies, and verify both stop. Preserve identity and delivery records for recovery. Reverify the binding before resuming, and never replay an uncertain send. Monitor authenticated inbound, duplicate/ignored, callback outcomes, accepted/uncertain sends, rejected signatures, window refusals and tokens needing reconnect by platform.

## Release tests and Meta review

| Test | Pass condition |
|---|---|
| Real inbox, ordinary sender | On each platform, a separate tester sends two successive messages. Each reaches the assigned agent once and receives the matching reply in the native inbox. Exercise role accounts first, then one eligible external business per approved channel. |
| Routing and retries | A signed batch containing two businesses, the same scoped string in different contexts, repeated IDs and simultaneous duplicate deliveries never mixes customers. Wrong signatures have no bot effect. Unknown or mismatched assets never activate a bot. |
| Reply policy and recovery | Cover just inside and at the 24-hour boundary, a callback reply token expiring before that boundary (default 30 minutes), an expired queue item, handover, a later multipart segment crossing expiry, a provider throttle and a timeout after acceptance. An Instagram part never exceeds 1,000 UTF-8 bytes. The UI identifies whether the NyxID reply token expired, the Meta window closed, or the provider outcome is uncertain. |
| Permissions and lifecycle | Test OAuth cancel/replay, forged asset choice, lost Page role, consent revocation, failed subscription, refresh, reconnect to the wrong account, disconnect during a send, competing claims, erasure and the second Page on the same grant. |
| Guest and rollout | Prove explicit guest enablement, correct model funding, isolated guest threads, omitted owner-token header, and absence of private owner tools. Test flag-off direct API access, existing bot management, suspension and an unaffected WhatsApp installation. |

At milestone 1, the app admin reads **App Review → Requests** for the actual App ID, records any draft or active request, and checks Business Verification separately. Continue building with role-approved assets while a request is pending. After staging passes, record the consent, asset selection, customer DM and visible reply for each channel. Provide reviewer access, test instructions, permission-by-permission rationale, privacy policy and data-deletion details. Request the minimum Advanced Access permissions demonstrated. If both products are on the same eligible app, group them when the dashboard permits. If it only permits the existing review, queue the new request after that decision. For distinct App IDs, use the matching app's submission. Public availability follows approval for that channel. The live dashboard state and ability to submit concurrently are unverified. [Meta App Review walkthrough](https://developers.facebook.com/documentation/resp-plat-initiatives/individual-processes/app-review/submission-guide) · [Business Verification](https://developers.facebook.com/documentation/development/release/business-verification)
