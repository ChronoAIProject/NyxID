## Implemented behavior

The manager accepts absent or whitespace-only storage configuration and renders no `storageClassName`. A configured name is normalized and validated as a Kubernetes DNS subdomain. Fresh provisioning verifies an existing explicit StorageClass or discovers the cluster default through bounded read-only API requests; missing/deleting/invalid classes, missing defaults and API/permission failures do not become successful readiness. Default discovery honors the stable and legacy annotations, newest creation time and Kubernetes name tie-break. StorageClass metadata is not a CSI Ready condition or physical-capacity proof.

UID/resourceVersion-guarded updates preserve the exact admitted workspace template, including whether its class was omitted. Today's configured class or default is not used to rewrite the retained PVC. Admission uses current configuration for CREATE and exact admitted template retention for UPDATE. Class-specific quota observations use a verified class for creation and retain unknown demand when the class is unresolved. No StorageClass writes or additional controller are introduced.

The ordinary `cli/Dockerfile.machine` and `cli/container/entrypoint.sh` match branch HEAD byte-for-byte. The hosted additions and pinned Heca/CMA stages now live in `cli/Dockerfile.machine-hosted`; `hosted-entrypoint.sh` contains the prior hosted startup implementation. The old `Dockerfile.machine-heca-cma` is absent and no `MACHINE_BASE_IMAGE` prerequisite remains. Shared browser/desktop/cua resources, protected Node identity and on-demand Heca/Codex authentication remain in use.
