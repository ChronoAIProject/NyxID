# Implemented security controls

This PR closes #1928, #1929, #1931 and #1940. It ships #1939 P1/P2: online OAuth revocation, the legacy-refresh upgrade, JWT key overlap and independent HMAC preparation. Issues #1930, #1933 and #1934 stay open for the deferred work listed below; #1939 P3 also remains deferred.

## Rollout

1. **Preserve HMAC keys before changing their AES/JWT sources.** Follow [key lifecycle preparation](security/KEY_LIFECYCLE.md): export the six existing final domain keys, protect the file and adopt it on every replica through `HMAC_KEYSET_PATH`. Adoption preserves exact bytes and historical audit/billing verification. New random replacements are not a supported rotation. Stage the next RSA public verifier on all readers before switching the active matching signer; retain old verifiers through token lifetimes and JWKS caches. See [JWT/HMAC configuration](ENV.md#independent-hmac-keyset-and-jwt-overlap).
2. **Coordinate OAuth authority rollout.** Follow [OAuth authority rollout](security/OAUTH_AUTHORITY_ROLLOUT.md) for the shipped legacy-refresh upgrade and coordinated issuer, delegation and callback drain.
3. **Deploy encryption readers first.** Follow [the mode matrix and reader-first procedure](ENV.md#contextual-encryption-writer-cutover) and [the migration API](SECURITY.md#encrypted-record-migration). Stage compatible readers with `CONTEXTUAL_RECORD_WRITES=false` and `ALLOW_LEGACY_RECORD_READS=true`, retaining every required provider/key. Drain incompatible readers and writers, including workers and long-lived connections. Only then set `CONTEXTUAL_RECORD_WRITERS_DRAINED=true` and `CONTEXTUAL_RECORD_WRITES=true`. The acknowledgement does not discover or stop old binaries. Run bounded migration/verification generations, resolve findings and pending families, then separately consider `ALLOW_LEGACY_RECORD_READS=false`. The [field inventory](security/ENCRYPTED_FIELD_INVENTORY.md) must agree with the registry; draining short-lived records instead of migrating them requires proof of their maximum lifetime and compatible writers. Backups and cloud-internal key versions require separate evidence before retirement. See also [KMS migration](KMS_MIGRATION_GUIDE.md) and [operations](KMS_OPERATIONS_GUIDE.md).
4. **Verify erasure completion before publishing a complete-erasure promise.** Use the [personal-erasure inventory/runbook](security/PERSONAL_ERASURE_INVENTORY.md) to review per-owner planning, durable provider effects and pending/operator-action/complete outcomes. Revocation is requested where supported; unsupported or unconfirmed effects need operator reconciliation. Preserve other owners' local resources and retained evidence. Complete collection coverage, exhaustive interruption/race tests and a retained-evidence status list remain follow-up work; acceptance alone does not establish complete erasure.

## Limits

- Personal erasure (#1930) has partial local coverage. Durable provider effects can remain pending or require operator action; acceptance is not a claim that every local/external copy has been deleted. Audit/billing history and required Machine lifecycle/fencing evidence remain, without an automatic purge or a fixed retention period. Account deletion does not purge operator-managed backups.
- All 12 pending encrypted-field families are named [above](#not-in-this-pr). Raw encrypt/decrypt entry points are still callable outside crypto; restriction of those methods and conversion of their callers remain unfinished under #1933/#1934. A partial inventory or zero old-key traffic cannot authorize strict global cutover or key retirement; the complete readiness report and retirement guard are deferred.
- Context binding protects its named ciphertext dimensions. It does not repair arbitrary database authorization changes, revoke credentials exposed in old copies or prove that transport/SDK memory is zeroized. Recipient-sealed/E2E material has a separate recipient key lifecycle.
- External offline JWT verifiers cannot observe NyxID's live authority checks immediately. Key compromise needs deliberate verifier retirement and client/cache coordination; normal overlap intentionally keeps old signatures valid.
- Self-service export, passkeys, organization-enforced MFA, audit TTL/retention implementation and external audit witnesses are not included in these changes. The privacy policy describes data-flow categories and supported rotation mechanics; the published contact supplies the deployment's sub-processor register, regions and request timelines. The operator decides backup retention and rotation schedules.
