# Implemented security controls

This document describes implemented controls and rollout constraints for #1928–#1931, #1933, #1934, #1939 and #1940. Account erasure (#1930), legacy-refresh compatibility (#1939), and encrypted-field coverage and secret-buffer handling (#1933/#1934) remain incomplete. Marked crosswalk rows need final verification as those implementations are completed.

## Rollout

1. **Preserve HMAC keys before changing their AES/JWT sources.** Follow [key lifecycle preparation](security/KEY_LIFECYCLE.md): export the six existing final domain keys, protect the file and adopt it on every replica through `HMAC_KEYSET_PATH`. Adoption preserves exact bytes and historical audit/billing verification. New random replacements are not a supported rotation. Stage the next RSA public verifier on all readers before switching the active matching signer; retain old verifiers through token lifetimes and JWKS caches. See [JWT/HMAC configuration](ENV.md#independent-hmac-keyset-and-jwt-overlap).
2. **Coordinate OAuth authority rollout:** ordinary legacy OAuth access/refresh tokens without protected consent are currently rejected; a constrained refresh upgrade is being added under #1939. Follow [OAuth authority rollout](security/OAUTH_AUTHORITY_ROLLOUT.md) for the refresh-upgrade rules and coordinated issuer, delegation and callback drain.
3. **Deploy encryption readers first.** Follow [the mode matrix and reader-first procedure](ENV.md#contextual-encryption-writer-cutover) and [the migration API](SECURITY.md#encrypted-record-migration). Stage compatible readers with `CONTEXTUAL_RECORD_WRITES=false` and `ALLOW_LEGACY_RECORD_READS=true`, retaining every required provider/key. Drain incompatible readers and writers, including workers and long-lived connections. Only then set `CONTEXTUAL_RECORD_WRITERS_DRAINED=true` and `CONTEXTUAL_RECORD_WRITES=true`. The acknowledgement does not discover or stop old binaries. Run bounded migration/verification generations, resolve findings and pending families, then separately consider `ALLOW_LEGACY_RECORD_READS=false`. The [field inventory](security/ENCRYPTED_FIELD_INVENTORY.md) must agree with the registry; draining short-lived records instead of migrating them requires proof of their maximum lifetime and compatible writers. Backups and cloud-internal key versions require separate evidence before retirement. See also [KMS migration](KMS_MIGRATION_GUIDE.md) and [operations](KMS_OPERATIONS_GUIDE.md).
4. **Verify erasure completion before publishing a complete-erasure promise.** The [personal-erasure inventory/runbook](security/PERSONAL_ERASURE_INVENTORY.md) must cover every personal collection, preserve other owners' local resources and retained evidence, and expose pending/operator-action/complete outcomes accurately. Current token-copy admission blocks provider revocation; its replacement with per-owner planning and durable provider effects is tracked in #1930. Verify that replacement, completion predicates and the retained list before removing the present limitations from security/privacy wording. Confirm the privacy policy's hosted retention, vendor and contact details with the deployment owner before publication.

## Limits

- Personal erasure (#1930) currently has partial local coverage and the `credential_copy_isolation_requires_external_reconciliation` remote blocker. Acceptance is not a claim that every local/external copy has been deleted. Audit/billing history and required Machine lifecycle/fencing evidence remain; no automatic audit purge is implemented here.
- The pending encrypted-field families under #1934 are `assistant_agent_learning_proposals`, `auth_device_codes`, `auth_device_codes_v2`, `device_codes`, `channel_bots`, `nyxbot_channels`, `nyxbot_threads`, `nyxbot_events`, `nyxbot_watches`, `oauth_clients`, `platform_entry_gateway_transports` and `platform_native_reply_handles`. Raw encrypt/decrypt entry points are still callable outside crypto; restriction of those methods and conversion of their callers remain unfinished under #1933/#1934. A partial inventory or zero old-key traffic cannot authorize strict global cutover or key retirement.
- Context binding protects its named ciphertext dimensions. It does not repair arbitrary database authorization changes, revoke credentials exposed in old copies or prove that transport/SDK memory is zeroized. Recipient-sealed/E2E material has a separate recipient key lifecycle.
- External offline JWT verifiers cannot observe NyxID's live authority checks immediately. Key compromise needs deliberate verifier retirement and client/cache coordination; normal overlap intentionally keeps old signatures valid.
- Self-service export, passkeys, organization-enforced MFA, audit TTL/retention implementation and external audit witnesses are not included in these changes. Hosted vendors, regions, contracts, fulfillment timelines and actual rotation practice require owner confirmation.
