## 1. Verification of the six upstream claims

### Claim 1 — `/mcp` already accepts delegated tokens. **CONFIRMED**

- `mcp_post` takes no `AuthUser` extractor; auth is manual per the comment at
  `backend/src/handlers/mcp_transport.rs:230` ("Auth helper (manual token
  validation, NOT AuthUser extractor)"); `authenticate_mcp` is defined at
  `mcp_transport.rs:365`.
- `AuthMethod::Delegated` is derived from `claims.act.is_some()` at
  `mcp_transport.rs:447-448`.
- The only scope gate on the JWT path is `auth::scope_allows_rest_proxy` at
  `mcp_transport.rs:416` (API-key path: `:381`), defined at
  `backend/src/mw/auth.rs:284` (claim said `:280`; minor line drift only). It is
  satisfied by `proxy` or `proxy:*` (`mw/auth.rs:284-286`, tests `:3141-3149`).
- A delegated token with `proxy:*` therefore reaches `tools/list` and
  `tools/call` on `/mcp` today.

### Claim 2 — #1430's "no narrower contract exists" premise conflated two routes. **CONFIRMED**

- The deny #1430 cited is the `mcp` family inside `delegated_read_denied_path`
  at `backend/src/mw/auth.rs:390-446` (the `"mcp"` literal is at `:405`; claim
  said `:401` — same block, line drift). That gate runs only inside the
  `AuthUser` middleware's delegated account-read branch
  (`mw/auth.rs:463-477`, applied at `:778-787`) and therefore governs
  `/api/v1/mcp/config`.
- Top-level `/mcp` is mounted directly via `mcp_billing_routes!`
  (`backend/src/routes.rs:192-217`) onto `mcp_transport` handlers that never
  invoke the `AuthUser` extractor, so the deny-family never runs there.
- So the factual premise of #1430 ("no assistant-safe replacement contract
  exists") was wrong as stated: a delegated `proxy:*` token can already
  *discover* tools via `/mcp`. What it cannot do is get admission-grade
  identity (claim 4) or be scope-bounded there (claim 3) — those are the real
  gaps, and #1439/#1440 are still the right shape of fix.

### Claim 3 — LIVE fail-open: `/mcp` ignores delegated service/node bounds. **CONFIRMED**

- `McpAuthContext::user()` hardcodes `allow_all_services: true` /
  `allow_all_nodes: true` (`mcp_transport.rs:272-273`).
- The only narrowing after construction is the relay branch: `relay_scope` is
  computed only when `claims.relay == Some(true)` (`mcp_transport.rs:426-433`)
  and applied at `:456-471`. Delegated and ordinary access tokens never get
  their claims-borne `allow_all_services` / `allowed_service_ids` /
  `allow_all_nodes` / `allowed_node_ids` applied.
- The `AuthUser` middleware path *does* honor those claims for
  `AccessToken | Delegated` at `mw/auth.rs:829-843` (with `unwrap_or(true)`
  legacy fallback) — that is the #1439-adjacent behavior `/mcp` lacks.
- PR #1441 changed 18 files (verified via `gh pr view 1441 --json files`);
  `mcp_transport.rs` is not among them.
- Consequence: a #1439-era delegated token minted with explicit
  `allowed_service_ids = [one service]` and `proxy:*` reads the owner's entire
  executable catalog through `/mcp` `tools/list`, and the per-service
  enforcement points (`mcp_transport.rs:576-620`, `:1884`) all see
  `allow_all=true`, so `tools/call` is also unbounded. This is a real security
  bug on the current base, independent of #1440's new route. It is fixed in
  this plan (step 2).

### Claim 4 — `/mcp` emits no admission-grade identity. **CONFIRMED**

- `grep catalog_digest|operation_digest backend/src/handlers/mcp_transport.rs`
  returns zero hits. `tools/list` emits LLM-shaped `McpToolDefinition`s
  (name/description/input_schema, `mcp_service.rs:222-227`) with flattened
  `slug__name` tool names — no `user_service_id`, no `endpoint_id`, no digests,
  no freshness fields.
- The only surface emitting `catalog_digest` + `endpoint_id` +
  per-operation digest is `GET /api/v1/mcp/config`
  (`handlers/mcp.rs:14,125,193`), which delegated tokens cannot reach
  (claim 2) and which #1440 forbids widening.
- So a delegated caller can discover tool *names* but cannot construct an
  exact-service approval per #1424 (`ExactServiceApprovalCreate` at
  `exact_service_approval_service.rs:36-46` requires `user_service_id`,
  `endpoint_id`, `catalog_digest`, `endpoint_contract_digest`,
  `operation_digest`). Genuine gap; this is the core of #1440.

### Claim 5 — #1424 digest helpers are orphaned. **REFUTED**

The three helpers and the opaque id are all live:

- `mcp_service::operation_catalog_digest`, `endpoint_contract_digest`,
  `exact_operation_digest` are consumed by the exact-service approval
  create/redeem resolution path at
  `backend/src/services/exact_service_approval_service.rs:524-528`
  (inside `resolve_exact_catalog`, used by both `create_request:117` and
  `redeem_request:276`), compared during authority replay checks at
  `services/approval_service.rs:667-670`, exercised by
  `billing_integration_tests.rs:655-663`, and emitted to callers by
  `handlers/mcp.rs:125` and `:193`.
- The opaque `op_` id (`opaque_operation_id`, `mcp_service.rs:1606-1616`) is
  not orphaned either: it *is* the `endpoint_id` minted for spec-derived
  endpoints at `mcp_service.rs:1152`, i.e. the identity that flows through the
  entire catalog and approval chain.
- Also refuted on `origin/main` (checked via
  `git show origin/main:backend/src/services/exact_service_approval_service.rs`
  — 21 references). The upstream analysis was almost certainly run against a
  pre-`d1a042c2` base (the failed #1430 worker's `b0292e7b`).

**Plan impact:** the issue's "create one canonical resolver and use it in three
places" is already ~done by #1424 for places (2) and (3). The facade must
*reuse* `load_operation_catalog` + `operation_catalog_digest`, not build
anything new. Any plan step that "unifies" the approval path onto a new
resolver would be re-implementing what exists.

### Claim 6 — `handlers/mcp.rs` has its own competing digest. **REFUTED (stale)**

- `handlers/mcp.rs:125` already calls the canonical
  `mcp_service::operation_catalog_digest`; there is no local `catalog_digest()`
  function anywhere in the file. Same on `origin/main`.
- The only residue is a stale, dangling doc comment at `handlers/mcp.rs:212-214`
  ("SHA-256 of canonical JSON…") sitting orphaned above `build_proxy_base_url`
  — clearly the remnant of the removed local fn. Cleanup only.
- The second half of the claim ("mcp.rs is the only handler emitting
  `catalog_digest`") is confirmed (`grep -rln catalog_digest backend/src/handlers`
  → only `mcp.rs`), plus `ExactServiceApprovalResult` echoes it from the
  approval service.

**Plan impact:** hypothesis item (d) ("migrate handlers/mcp.rs off its local
digest") is already shipped. Only the comment deletion remains.

### Bonus verification — what #1439/PR #1441 actually provides

Because the facade builds directly on it:

- `models/catalog_delegation_grant.rs` — `catalog_delegation_grants`
  collection keyed by JWT `jti`, storing owner, actor client, receiving
  client, scope, resources, and explicit `allow_all_services/allowed_service_ids`
  + `allow_all_nodes/allowed_node_ids`, `revoked`, `expires_at`.
- `services/catalog_delegation_service.rs` — `persist_grant` (called from
  `token_exchange_service.rs:225,427` at mint), `validate_live_grant:82`
  (deny-by-default: grant lookup by jti/unrevoked/unexpired, claim↔grant
  equality, both clients active + delegation-scope-registered, consent, service
  ids grantable, node ids owned), `authority_from_claims:200` (every claim must
  be `Some`; `allow_all` + nonempty list is rejected; empty list stays deny-all).
- The `AuthUser` middleware already calls `validate_live_grant` for **every**
  delegated token whose scope contains `mcp:catalog:read`, before route
  dispatch (`mw/auth.rs:763-772`). So by the time a handler sees a delegated
  `AuthUser` with the catalog scope, the explicit authority claims are proven
  present, consistent, and grant-backed — the `unwrap_or(true)` legacy fallback
  at `mw/auth.rs:834-835` provably cannot have fired for that token.
- `mcp:catalog:read` is registered for delegation
  (`oauth_client_service.rs:48`) and deliberately does **not** satisfy
  `scope_allows_rest_proxy` (asserted at `mw/auth.rs:1503-1504`).
- Scope shipped inert as claimed: nothing outside mint/validation consumes it
  yet (`grep MCP_CATALOG_READ_SCOPE` → registries, mint, guards only).

## 2. Scope verdict: new route, but thinner than the issue implies

**Verdict: build the dedicated route `GET /api/v1/delegation/operation-catalog`
(the issue is right about the route), and do NOT extend `/mcp`. But the
"canonical resolution" work item is mostly already satisfied by #1424, so the
implementation is a projection handler over existing services, not a new
resolver. Additionally fix the claim-3 fail-open in `mcp_transport.rs` as part
of this work — it is required for the issue's "enforce the explicit service and
node bounds" outcome to be true anywhere delegated tokens can already reach.**

Adjudication of the competing hypothesis, item by item:

**(a) Enforce delegated service/node scope at `mcp_transport.rs:~457` — YES,
do it, but it is not a substitute for the facade.** It closes a live fail-open
(claim 3) and is ~15 lines mirroring `mw/auth.rs:829-843`. It does not produce
admission-grade discovery: after the fix, a delegated caller still sees only
LLM-shaped tool names with no ids/digests (claim 4).

**(b) Teach `/mcp` to accept `mcp:catalog:read` — NO for this delivery.**
This is a route-choice tradeoff, not a claim that method-level admission is
impossible. A rejected alternative would add an explicit JSON-RPC method matrix
(`initialize`/`tools/list`/`ping` only), reject `tools/call`, generic proxy, and
mutating meta-tools, and extract live-grant validation into a shared helper.
That keeps the existing MCP client surface but adds protocol/session coupling,
another projection to maintain, and a larger audit surface. The dedicated
typed route is the lower-risk contract for #1440.

1. `/mcp` is an execution transport. `tools/call` and the generic proxy tool
   live behind the same scope gate (`mcp_transport.rs:416`). Admitting a
   read-only scope would require bifurcating scope semantics per JSON-RPC
   method inside the dispatcher. #1439 is explicit that the scope "must not
   imply … generic proxy access … or effect authority", and the repo already
   asserts `mcp:catalog:read` ⇏ proxy (`mw/auth.rs:1503-1504`). Wiring it into
   the proxy gate inverts a shipped invariant.
2. The #1439 fail-closed machinery (`validate_live_grant`) runs in the
   `AuthUser` middleware, which `/mcp` bypasses by design. Admission at `/mcp`
   means duplicating the live-grant check inside `authenticate_mcp`'s manual
   auth — a second divergent enforcement copy of exactly the kind FI-005 and
   the CLAUDE.md layer rules exist to prevent.
3. `/mcp`'s auth matrix is deliberately legacy-tolerant (API keys, session
   fallback, expired-JWT-with-live-session, `mcp_transport.rs:352-364,478-484`).
   #1440's matrix is deny-by-default with "legacy tokens never admitted".
   Grafting deny-semantics onto a tolerate-semantics surface is where fail-opens
   come from; the current claim-3 bug is itself evidence.

**(c) Add #1424 identity/digest fields to `/mcp` output — NO for admission.**
MCP tool definitions are name/description/inputSchema (`mcp_service.rs:222-227`);
service/endpoint identity is deliberately flattened away. Grafting
`catalog_digest`/`endpoint_contract_digest`/ids via `_meta` would create a
*third* projection of the catalog that consumers must parse out of a protocol
extension — strictly worse than a typed DTO on both the "no second catalog"
constraint and consumer ergonomics (the consumer, Aevatar, needs typed fields
to construct `ExactServiceApprovalCreate` bodies). The issue's own suspicion
here is correct.

**(d) Migrate `handlers/mcp.rs` off its local digest — already done** (claim 6).
Residual work: delete the stale comment at `mcp.rs:212-214`.

**On #1440's internal tension** ("no second catalog" vs specifying a third
projection): the resolution is that the facade must contain **zero new
resolution or digest logic** — it is a filtered *view* of
`load_operation_catalog` output, digested by the same
`operation_catalog_digest` call the approval path uses. After this plan the
codebase has: one loader, one digest function, one digest input semantic, four
call sites (mcp/config, approval create, approval redeem, facade), minus the
historical local digest (already gone). Divergent digest computations do not
increase. (Pre-existing and out of scope: `durable_operation_grant_service.rs:122`
has its own `endpoint_contract_digest` over the *model-level* `ServiceEndpoint`
— a different input type serving durable grants; unifying it would change
shipped grant digests for no #1440 benefit.)

### Deliberate deviation: what `catalog_digest` hashes

#1440's response contract says `catalog_digest` is "the digest of the final
caller-visible, generic-free, deterministically sorted view". Its acceptance
criteria simultaneously require "catalog output and delegated exact-approval
create/redeem use the same resolver and canonical digest semantics". **These
two demands conflict**, because the approval path digests
`catalog.services` as returned by `load_operation_catalog`
(`exact_service_approval_service.rs:524`), and that set *retains* generic-proxy
services (`load_operation_catalog` filters scope, executability, and contract
validity at `mcp_service.rs:480,515,529`, but keeps `is_generic_proxy` rows —
they are only counted at `:541-544`).

I resolve in favor of the acceptance criterion with teeth: **the facade emits
`operation_catalog_digest(&catalog.services)` — byte-identical to what approval
create and redeem compute for the same caller — while the response body lists
only the generic-free, user-managed subset.** Rationale:

- The digest's entire job is drift detection across discovery → create →
  redeem. A generic-free digest would *never* equal the approval path's digest
  for any owner with a generic service in scope, breaking the chain the issue
  itself mandates. Making approvals digest a generic-free view instead would
  change shipped #1424 digest values (a live external contract with Aevatar per
  aevatarAI/aevatar#3377) and also desynchronize `/api/v1/mcp/config`'s digest
  — strictly more divergence.
- There is no security cost: the digest is an opaque hash; including generic
  rows in its input discloses nothing to the delegated caller.
- Known cosmetic consequence, stated plainly: an owner adding/removing a
  generic-proxy service changes the delegated caller's `catalog_digest` without
  changing the caller's visible list. That is exactly the drift behavior
  approvals already have today, and re-fetching the catalog is the documented
  recovery.

This deviation is listed again in §5.

## 3. Implementation plan

### Step 0 — baseline
`cargo check -p nyxid` and the exact-service suite green on the branch tip
before any change (with `NYXID_TEST_DATABASE_URL=mongodb://127.0.0.1:27017/?directConnection=true`;
a ~13s mass failure = Mongo connection failure, not regressions).

### Step 1 — `backend/src/mw/auth.rs`: expose the token's `jti` on `AuthUser`
Add `pub token_jti: Option<String>` to `AuthUser`, populated from `claims.jti`
in the JWT branch (`mw/auth.rs:845-865`), `None` on the API-key, session, and
service-account paths. ~29 struct-literal construction sites (mostly tests)
updated mechanically.

Why: the facade handler must resolve authority from the **online grant record**
(`catalog_delegation_grants`, keyed by jti), not from `AuthUser`'s
claims-materialized bounds — the issue forbids inferring authority from
`AuthUser` defaults, and the grant also carries `expires_at`, which is the
`authority_expires_at` the DTO needs (equal to token `exp` by construction,
`catalog_delegation_service.rs:44-78`). This also buys a second
revocation/expiry check at read time (FI-004: the grant is the authoritative
cross-process record).

### Step 2 — `backend/src/handlers/mcp_transport.rs`: close the claim-3 fail-open
In `authenticate_mcp`, after the relay block (`:455-471`), apply the same
narrowing the `AuthUser` middleware applies at `mw/auth.rs:829-843`: for
`AuthMethod::AccessToken | Delegated`, set
`ctx.allow_all_services = claims.allow_all_services.unwrap_or(true)` (same for
nodes and the two id lists). Legacy tokens without claims keep allow-all —
identical semantics to the middleware, no behavior change for them. Existing
enforcement points (`:576-620`, `:1398-1417`, `:1884`) then work unmodified.

This is a security fix shippable in the same PR (it is the "enforce the
explicit service and node bounds from #1439" acceptance line applied to the
surface delegated tokens already reach). If review prefers, it can be split
into its own fast-tracked PR that #1440's PR then rebases on.

### Step 3 — `backend/src/handlers/delegation.rs`: the facade handler + DTOs
New handler `get_operation_catalog(State, AuthUser) -> AppResult<Json<DelegatedOperationCatalogResponse>>`.
Gate order (each failure fail-closed, no state change):

1. `auth_user.auth_method == AuthMethod::Delegated`, else 403
   (`AppError::Forbidden`). This rejects sessions, plain access tokens, API
   keys, service accounts, and relay tokens (relay tokens have no `act` so they
   materialize as `AuthMethod::Relay`). Note the route is reachable by any
   delegated token because `/api/v1/delegation` is a delegated-native path
   (`mw/auth.rs:371-385`) — the handler gates are therefore mandatory, and are
   the reason no `delegated_read_denied_path` entry is needed (that list governs
   the `account:read` GET fallback, which never applies to native paths).
2. `catalog_delegation_service::scope_has_catalog_read(&auth_user.scope)`,
   else 403 — legacy delegated tokens (e.g. `proxy:*`-only) are never admitted.
3. Load `CatalogDelegationGrant` by `auth_user.token_jti` with
   `revoked: false, expires_at > now`; deny with the same not-found-shaped
   `invalid_catalog_authority()` error (`catalog_delegation_service.rs:334`,
   `AppError::Unauthorized`) if absent. Cross-check
   `grant.user_id == auth_user.user_id`,
   `grant.actor_client_id == auth_user.acting_client_id`,
   `grant.receiving_client_id == auth_user.oauth_client_id`, and that the
   grant's authority equals `AuthUser`'s materialized bounds — any mismatch
   denies. (The middleware's `validate_live_grant` at `mw/auth.rs:763-772`
   already proved most of this; the handler re-derivation is defense in depth
   and the source of `authority_expires_at`.)
4. Build scopes exactly as the approval path does
   (`exact_service_approval_service.rs:487-497`):
   `NodeScope::Allowed/Unrestricted` and `ServiceScope::Allowed/Unrestricted`
   from the grant's `allow_all_*`/`allowed_*_ids`. Empty list + `allow_all:
   false` yields `Allowed(&[])`, which permits nothing
   (`mcp_service.rs:455-462`) — deny-all preserved, response is a valid empty
   catalog (authority is real, it just grants nothing; this is a 200, not an
   error — authority *failures* are 401/403).
5. `mcp_service::load_operation_catalog(&state.db, node_ws_manager,
   &auth_user.proxy_resolution_user_id(), node_scope, service_scope)` — the
   same user-id derivation the approval caller uses
   (`handlers/exact_service_approvals.rs:95`), guaranteeing resolver-input
   identity with create/redeem.
6. `catalog_digest = mcp_service::operation_catalog_digest(&catalog.services)`
   (§2 deviation: digest over the full scoped catalog, matching approvals).
7. Project the response list: retain only services where
   `source` is `McpToolSource::UserManaged` **and** `!is_generic_proxy`.
   (`load_operation_catalog` has already removed non-executable and
   invalid-contract services and sorted deterministically,
   `mcp_service.rs:515-539`; `nyx_generic_proxy_v1` endpoints only exist on
   generic services, so excluding those services excludes that endpoint id.)
   Platform-wide fallbacks are excluded by the `UserManaged` filter.

DTOs (dedicated response structs per CLAUDE.md; no model serialization):

```rust
DelegatedOperationCatalogResponse {
    contract_version: &'static str,        // "nyxid-delegated-operation-catalog.v1"
    catalog_digest: String,
    resolved_at: String,                   // RFC3339, now at resolution
    authority_expires_at: String,          // RFC3339, grant.expires_at (== token exp)
    services: Vec<DelegatedCatalogService>,
    total_services: usize,
    total_operations: usize,
}
DelegatedCatalogService {
    user_service_id: String,               // exact UserService id (== service_id for UserManaged)
    service_slug: String,
    service_name: String,
    description: Option<String>,
    node_id: Option<String>,               // node scope identity from McpToolSource::UserManaged
    operations: Vec<DelegatedCatalogOperation>,
}
DelegatedCatalogOperation {
    endpoint_id: String,                   // opaque op_… for spec-derived endpoints
    name: String,
    method: String,
    path: String,                          // normalized template
    parameters: Option<serde_json::Value>,         // already publishability-bounded
    request_body_schema: Option<serde_json::Value>,
    request_content_type: Option<String>,
    request_body_required: bool,
    response: OperationResponseContract,   // bounded output contract
    endpoint_contract_digest: String,      // mcp_service::endpoint_contract_digest
}
```

Nothing else. No credentials, tokens, headers, hashes, auth config, upstream
bodies (none of these exist on `McpToolService`/`McpToolEndpoint` anyway — the
projection types cannot express them, which the secret-free test then locks in).
No writes, provider invocation, approval mutation, or credential mutation: the
handler performs Mongo `find` reads via `load_operation_catalog` and the grant
lookup. The canonical loader may perform a hardened, cached, DNS-pinned
outbound fetch for a user-mounted OpenAPI document. Logging: a metadata-only
`tracing::info!` mirroring the `delegated_account_read` line
(`mw/auth.rs:796-804`) — ids and counts, never catalog content.

### Step 4 — `backend/src/routes.rs`: mount
Add `.route("/operation-catalog", get(handlers::delegation::get_operation_catalog))`
to `delegation_routes` (`routes.rs:907-910`), which is already nested in the
delegated-allowed group (`:1391`). Pure read → no billing-route registration
(only redeem is billed MCP egress, `handlers/exact_service_approvals.rs:53-54`).

### Step 5 — `backend/src/handlers/mcp.rs`: delete the stale dangling comment
Remove lines 212-214 (orphaned doc text above `build_proxy_base_url`).

### Step 6 — docs + release notes
- `docs/API.md`: route entry, DTO contract, digest semantics (including the §2
  deviation and how a consumer computes `exact_operation_digest` from the

- Release-notes entry per repo convention (producer contract shipped;

1 (AuthUser field) → 3/4 (facade) in one chain; 2 (mcp_transport fix) and 5

## 4. Test plan

Backend tests require a MongoDB replica set:
`NYXID_TEST_DATABASE_URL=mongodb://127.0.0.1:27017/?directConnection=true`.
Mass failure of ~5000 tests in ~13s = connection failure, not regressions.

### Fail-closed matrix (from #1440 acceptance), route-level

Integration tests (real Mongo, mounted router) in a new
`backend/src/handlers/delegation.rs` test module or alongside the existing
exact-service integration tests:

| Case | Setup | Expected |
|---|---|---|
| Happy path | Owner with 2 connected typed UserServices + 1 generic; delegated token minted through token exchange with `mcp:catalog:read`, `allow_all_services=false`, `allowed_service_ids=[svc A]` | 200; only service A listed; generic absent; `catalog_digest` equals `operation_catalog_digest` of the same scoped resolution; `authority_expires_at` == grant expiry |

| Non-delegated callers | Session cookie, plain access token, API key, service account, relay token | 403 each (relay additionally lacks `act`) |

| Revoked authority | `revoked: true` on grant | 401 |
| Disabled client | actor or receiving `OauthClient.is_active=false` | 401 via middleware `validate_live_grant` |

### Determinism / snapshot
- Two consecutive facade calls for the same fixture return byte-identical JSON
  (ordering from `load_operation_catalog`'s sort, `mcp_service.rs:517-522`).
- Digest invariance under object-key reordering already covered by
  `canonical_sha256` tests; add a facade-level snapshot of the DTO for a fixed
  fixture.
- Secret-free DTO: serialize a populated response, assert absence of
  `credential|token|authorization|secret|hash|api_key` keys anywhere in the
  JSON tree (pattern: `handlers/mcp.rs:336-353`).

### Drift detection proof (discovery → create → redeem)
1. Fetch facade catalog as the delegated caller; take `catalog_digest`,
   `endpoint_contract_digest`, `endpoint_id`, `user_service_id`.

## 5. #1440 acceptance items I recommend NOT building, and why

1. **"Generic-free digest" as literally specified.** The facade's
   `catalog_digest` will be the canonical digest over the scoped
   `catalog.services` (which retains generic rows), because the approval
   create/redeem path digests exactly that
   (`exact_service_approval_service.rs:524`) and the issue's own acceptance
   requires identical digest semantics across catalog output and
   create/redeem. A generic-free digest would either break that equality or
   force changing shipped #1424 digest values (an external contract with
   Aevatar). The *listing* is fully generic-free as specified. If the reviewer
   insists on literal compliance, the coherent alternative is a coordinated
   migration of **all four** call sites to an admission-view digest in one
   release (accepting one transient `catalog_drift` rejection window for
   in-flight approvals) — I recommend against it now; it can be a follow-up.

2. **"Operation generation/freshness fields required by exact approval" as a
   server-emitted catalog field.** Verified: `operation_generation` has no
   server-side origin in the catalog. It is caller-supplied at create
   (`ExactServiceApprovalCreate.operation_generation`,
   `exact_service_approval_service.rs:43`), stored on the binding
   (`:198-199`), and fence-compared at redeem (`ensure_fence`) — i.e. it is a
   caller-chosen identity/idempotency anchor, like `operation_id` and
   `idempotency_key`, not a catalog attribute. Same for `operation_id` (also
   caller-supplied and never compared against the catalog at create). Minting
   a fake "generation" in the facade would imply server semantics that do not
   exist and could not be verified at redeem. The facade's freshness fields
   are the ones that are real: `resolved_at`, `authority_expires_at`,
   `catalog_digest`, `endpoint_contract_digest`. The DTO documentation will
   state explicitly that `operation_id`/`operation_generation`/
   `idempotency_key` are caller-generated per the #1424 contract.

3. **A new canonical resolver.** The issue's "create one canonical
   exact-operation resolver/projection and use it for [catalog, create,
   redeem]" is already satisfied for create/redeem by #1424's
   `resolve_exact_catalog` over `load_operation_catalog` (claim 5 refutation).
   The facade adds a fourth consumer of the existing loader + digest, plus a
   pure projection. No new resolution code is built — building one would
   *create* the second catalog the issue forbids.

4. **Aevatar canary work.** Out of delivery boundary per the issue itself
   (integration acceptance lives in aevatarAI/aevatar#3364/#3366/#3377).

5. **New numeric error codes.** Failures reuse existing `AppError` variants
   (`Unauthorized` via `invalid_catalog_authority`, `Forbidden` for
   method/scope gates). No new reserved block is warranted for a pure-read
   facade; CLAUDE.md's code table stays untouched.
