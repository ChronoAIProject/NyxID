# Adversarial review record (Astra, Codex gpt-6-astra xhigh), 2026-09-14

Phase 1 below is the pre-plan attack list, verbatim. Phase 2 (6 BLOCKER + 17 MAJOR against the v1 draft) is integrated into the plan's section 12 and its per-section rewrites; the v2 plan is the authoritative resolution of every phase-2 finding.

## Phase 1: attacks any design must withstand

**Phase 1 adversarial review:** NyxID has substantial support for hosted credential setup, OAuth consent, scoped service access, and recovery from interrupted flows. The missing contract is **“this app, acting for this user and owner, can perform these required operations using these specific connections, as observed at this time.”** Neither a completed Connect Link nor an active credential establishes that contract.

This is a static, read-only review of the requested backend, frontend, SDK, and documentation paths. No files were edited and no live provider requests were made. The numbered items below identify attacks the forthcoming design must withstand, along with existing protections and their limits.

1. **“Connected” can produce a false success immediately.** Hosted API-key completion provisions a service and calls `finish_claim`; OAuth completion checks for an active stored credential. Neither establishes that the downstream accepts the credential. The LLM status endpoint similarly maps stored `active` to `ready`, including a ready result for a service without an API-key reference. **Existing coverage:** these mechanisms establish provisioning state and some local eligibility. They are useful prerequisites, but their success values cannot become onboarding health evidence. See [connect completion](<backend/src/services/connect_link_service.rs:439>) and [LLM status resolution](<backend/src/services/llm_gateway_service.rs:295>).

2. **“Working” is underspecified enough to make almost any probe dishonest.** A public `/health` response proves reachability; `/user` may establish token identity; a model-list response does not prove permission or credit to run CMA’s chosen model. GitHub authentication does not establish access to a required repository, organization SSO authorization, or write capability. Require a named, versioned validation profile with an explicit claim and distinguish authenticated, operation-capable, temporarily unavailable, and unsupported validation. **Existing coverage:** there is an AWS-specific creation probe, but it intentionally allows network errors and 5xx through. Copying that success contract would violate this feature’s requirement. See [existing cloud credential verification](<backend/src/handlers/keys.rs:29>).

3. **The human’s successful test may validate a credential the app will never use.** A browser session can reach a service that the app’s OAuth token cannot; an agent binding can substitute a different credential; routing can select an org connection, node, fallback, master credential, or overridden destination. A separate raw `reqwest` probe can bypass the exact policy, billing, and routing failures the app will encounter. **Existing coverage:** execution-authority projections already identify destination, credential ID/epoch, overrides, master-credential use, injection configuration, policy, and node bindings. Validation needs equivalent resolution under the intended caller context. See [execution-authority projection](<backend/src/services/execution_authority.rs:20>) and [agent credential resolution](<backend/src/services/proxy_service.rs:2877>).

4. **“The user’s own GitHub OAuth token” is dangerously ambiguous.** It must not accidentally accept a PAT, a platform master credential, or another person’s org-shared connection. Conversely, `credential_source = "platform"` means the connection uses NyxID’s OAuth **application credentials**; the resulting access token can still represent the user’s GitHub authorization. Rejecting every platform-source connection would force unnecessary BYO OAuth applications. Define accepted credential types, provider identity, ownership, and any required upstream-account relationship independently. **Existing coverage:** `UserApiKey` records credential type, provider, connection ID, scopes, and OAuth-client provenance, but those fields do not alone establish upstream human identity. See [credential and provenance fields](<backend/src/models/user_api_key.rs:15>).

5. **Three different permission systems can be collapsed into one misleading checkbox.** NyxID OAuth scopes authorize actions against NyxID; downstream OAuth scopes authorize GitHub/Google/etc.; service grants and approval policies authorize particular NyxID execution paths. A user can satisfy two and still fail the third. An app may reasonably require GitHub specifically, but the UI must disclose that requirement and let the user decline; an “any LLM” requirement must not quietly become “connect our preferred provider.” **Existing coverage:** consent stores explicit service selection, while shared downstream OAuth applications enforce vetted scope allowlists. The manifest must preserve both boundaries and must not bypass provider scope limits. See [consent grant construction](<backend/src/handlers/oauth.rs:807>) and [downstream scope enforcement](<backend/src/services/user_token_service.rs:706>).

6. **Using `service_category = "provider"` for “any LLM provider” is a concrete implementation trap.** That value means an OIDC service for which NyxID is the identity provider. The other categories are `connection` and `internal`; they are not capability categories. Current LLM discovery uses the `llm-` catalog-slug prefix plus provider configuration, and gateway model routing has its own mapping. **Existing coverage:** existing LLM discovery provides a starting candidate set, but there is no equivalence between the category field and LLM compatibility. Require a deliberate capability selector and define whether custom OpenAI-compatible endpoints qualify. See [category semantics](<backend/src/models/downstream_service.rs:224>) and [LLM selection and routing](<backend/src/services/llm_gateway_service.rs:327>).

7. **“Any one of these providers” can validate one candidate and execute another.** Users may have several connections to the same provider, including one expired connection, one working connection, and an org connection they cannot delegate. A `find_one` or provider-level boolean can yield false negatives, nondeterministic selections, or a green result followed by routing to the wrong connection. The result must retain the concrete satisfying `UserService` IDs, enforce the requirement’s owner policy, and bind selection to the app’s grant and execution behavior. **Existing coverage:** active service listings expose personal/org sources and access, but the current LLM helper resolves a single matching service per owner/catalog pair. See [LLM candidate lookup](<backend/src/services/llm_gateway_service.rs:291>) and [catalog-service lookup](<backend/src/services/user_service_service.rs:644>).

8. **A requirements manifest with unclear authority is either forgeable or unmaintainable.** If requirements come solely from request parameters, a caller can remove GitHub or substitute an easier probe and obtain “success.” If only a mutable `OauthClient` blob exists, in-flight sessions have no stable contract. A new collection also adds little unless its ownership, versioning, and session relationship are explicit. My review baseline would be an app-owned published definition, with each run binding its version or immutable snapshot; request parameters may select authorized variants under explicit rules. **Existing coverage:** `default_service_catalog_slugs` is expressly a UI hint, not a requirement or grant. Preserve that meaning for existing clients. See [OAuth client defaults](<backend/src/models/oauth_client.rs:47>) and [developer-app write ownership](<backend/src/handlers/developer_apps.rs:20>).

9. **Changing requirements during onboarding creates either silent escalation or a false attestation.** App A adds a write scope after the user reviewed its request; a catalog admin changes the probe; a service disappears; an older replica ignores a new requirement operator. The final result must identify the exact requirement and validation versions reviewed and evaluated. Unknown mandatory predicates must fail closed. Revisiting a stable link also needs a stated rule for whether it uses the latest published requirements. **Existing coverage:** signed consent requests bind reviewed authorization inputs, and exact approvals version their authority digests and handle drift. These are precedents, not an existing onboarding-version mechanism. See [signed consent request](<backend/src/handlers/oauth.rs:562>) and [versioned execution binding](<docs/GRANULAR_APPROVALS_DESIGN.md:320>).

10. **RFC 8707 resources cannot simply become a shopping list of missing services.** A NyxID resource URI identifies a concrete, active, accessible user service. It does not express “create GitHub” or “any LLM.” Connecting a new service after token issuance also does not insert that service into an existing token’s `allowed_service_ids`; refresh cannot be used to silently expand the original grant. **Existing coverage:** resource resolution and narrowing already enforce these distinctions. Resolve requirements to concrete services, obtain explicit grants, and issue appropriately scoped tokens at the defined completion point. Never solve onboarding by switching to `allow_all_services`. See [resource resolution](<backend/src/services/oauth_resource_service.rs:98>) and [resource narrowing](<backend/src/services/oauth_resource_service.rs:73>).

11. **Existing Connect Links cannot directly represent an unknown user arriving from App A.** Creation currently binds the link to the authenticated creator’s user ID. A public reusable app entry URL needs a separate point at which NyxID authenticates the human and binds that run to an account. Otherwise an attacker can pre-create a flow and persuade a victim to complete it, or a user switching browser accounts can attach credentials to the wrong run. Org ownership must be explicitly selected and authorized, not inferred from a convenient available connection. **Existing coverage:** completion requires owner write access; signed consent checks the authenticated subject. Preserve those protections through every provider return. See [link creation identity](<backend/src/handlers/connect_links.rs:205>) and [completion owner check](<backend/src/services/connect_link_service.rs:742>).

12. **Account isolation is not app isolation.** App B acting for the same NyxID user should not automatically read, cancel, or redeem App A’s onboarding run. Current Connect Link read/cancel paths pass the actor user ID and link ID; their service-layer ownership checks do not compare the caller’s OAuth client ID with `requesting_app_id`. Copying that interface would inherit account-level access for potentially much richer onboarding results. **Existing coverage:** link creation derives app attribution from the authenticated token, and unrelated accounts are blocked. A new app-specific protocol still needs explicit app binding on status, cancellation, results, and subscriptions, with a separate human management path. See [status handler](<backend/src/handlers/connect_links.rs:250>) and [actor-scoped lookup](<backend/src/services/connect_link_service.rs:232>).

13. **Co-branding can turn NyxID into a phishing endorsement.** Registering an OAuth client named “CMA” does not prove it is Calvin’s CMA. Request-body `requested_by`, URL query text, arbitrary logos, and markdown explanations must not become trusted identity. The current consent frontend reads `client_name` from the query string, so it is particularly unsuitable as the authority for a stronger branded trust signal. **Existing coverage:** app-bound Connect Links replace supplied attribution with the registered client’s name, and developer-app mutations have ownership checks. Neither establishes brand ownership. Render identity from authoritative app data, distinguish verified identity from self-asserted names, show the destination domain, and constrain branding assets/content. See [attribution resolution](<backend/src/services/connect_link_service.rs:152>) and [consent display inputs](<frontend/src/pages/oauth-consent.tsx:105>).

14. **“Reuse OAuth callback validation” does not mean “registered exact match.”** `oauth_service::validate_client` accepts exact registered URIs, but also accepts loopback URLs and private-use schemes for public clients. Its security rationale explicitly depends on PKCE. Connect Links call this validator, yet their terminal callback contains status and an ID, not a PKCE-bound authorization code. A new callback policy must deliberately address native-client exceptions, intercepted custom schemes, and app deactivation or callback changes during the run. **Existing coverage:** active-client checks, exact matching for ordinary web destinations, and Connect Link rejection of userinfo/fragments and certain dangerous schemes. The exceptions require explicit review for the new protocol. See [OAuth redirect policy](<backend/src/services/oauth_service.rs:21>) and [Connect Link callback validation](<backend/src/services/connect_link_service.rs:1268>).

15. **A browser `status=success` is forgeable, and a richer callback can leak credentials or account data.** Apps must correlate the return with their own pending request and verify the result through an authenticated, app-bound lookup or a short-lived, single-use exchange. Never put downstream tokens, access/refresh tokens, detailed probe responses, or a reusable capability in the callback. Validate correlation for failure returns too: the current OAuth SDK throws on an `error` parameter before checking stored state. Long-lived entry links also need protection against token exposure through analytics, logs, browser history, and embedded resources. **Existing coverage:** Connect Link terminal callbacks add only status and link ID; ordinary SDK success callbacks verify state and use PKCE. See [terminal callback construction](<backend/src/services/connect_link_service.rs:1346>) and [SDK callback handling](<sdk/oauth-core/src/index.ts:171>).

16. **Live validation introduces authenticated SSRF and credential exfiltration.** A probe URL, overridden service endpoint, absolute “relative” path, redirect, or rebinding hostname can send credentials to metadata services, internal infrastructure, or an attacker. Validating a URL once when storing it does not bind the later network connection. Self-hosted services and node-local destinations need an explicit execution boundary. **Existing coverage:** hosted user-endpoint validation rejects private targets; the spec fetcher additionally pins DNS, disables redirects, applies timeouts, and bounds response bytes. Webhook URL validation provides useful admission checks but is not itself a complete probe transport. See [endpoint validation](<backend/src/services/url_validation.rs:121>) and [pinned fetch client](<backend/src/services/api_docs_service.rs:1041>).

17. **A generic catalog “probe definition” can become an arbitrary credentialed execution engine.** Allowing an app manifest to supply URLs, methods, headers, bodies, templates, or unrestricted response expressions lets the app run operations before execution consent. Even a GET is not universally free of side effects. Prefer reviewed, versioned validator profiles with fixed origin/path constraints, bounded inputs, documented effects, and a defined parser; apps select profiles they are permitted to require. Custom services without a supported validator must report that limitation. **Existing coverage:** catalog metadata and operation discovery exist, but I found no general validation-profile contract in the reviewed connection paths. Existing exact approvals illustrate the necessary separation between observation and credential-materializing execution. See [ordered authority evaluation](<backend/src/services/exact_service_approval_service.rs:1376>) and [credential materialization boundary](<backend/src/services/exact_service_approval_service.rs:437>).

18. **Validation can spend the user’s money without delivering user value.** “Send a tiny completion” still incurs provider charges, rate limits, audit events, and potentially NyxID billing. Validating every candidate on every revisit amplifies that cost; retrying an ambiguous timeout may charge twice. Specify whether NyxID, the app, the person, or an org pays, and whether any chargeable validation needs explicit approval. **Existing coverage:** normal LLM execution resolves the resource owner, checks approval, and opens billing before forwarding. A standalone validator would bypass those protections unless deliberately integrated. A non-billable identity probe must advertise the narrower guarantee it provides. See [LLM approval and billing admission](<backend/src/handlers/llm_gateway.rs:344>).

19. **A reusable link can become a validation DoS endpoint.** Link previews, browser prefetch, React remounts, reconnects, repeated polling, multiple tabs, and many published app links can multiply upstream calls. An attacker can also exhaust a provider-wide quota through many users. Admission needs per-app, per-user/owner, per-credential/provider, and overall concurrency limits, bounded fan-out and retry budgets, plus shared coordination across replicas. Status polling should observe a validation job rather than start another one. **Existing coverage:** Connect Links already have shared creation/preview/completion limiters; outbound app webhooks have shared per-app admission. Those limiters do not currently account for probe work. See [Connect Link admission](<backend/src/handlers/connect_links.rs:192>) and [shared webhook admission](<backend/src/services/developer_webhook_service.rs:106>).

20. **Validation can become an account and resource-existence oracle.** Detailed results can reveal which providers a user has, employer/org memberships, GitHub repository existence, accessible model names, or whether a credential has a privileged scope. Provider bodies and error messages may expose more than the requirement warrants. Public entry/preview surfaces must not enumerate user connections, and an app should receive only the evidence authorized for its selected requirements. **Existing coverage:** existing Connect Link preview is restricted to setup metadata, unauthorized owner access is not-found-shaped, and provider callback failures use normalized error codes. Extending these responses with arbitrary probe diagnostics would discard those protections. See [public preview response](<backend/src/handlers/connect_links.rs:52>) and [stored link error fields](<backend/src/models/connect_link.rs:56>).

21. **Multi-step completion needs more than several single-use links.** Two tabs can provision duplicates; polling can observe a child completed before validation; cancellation can race the last successful probe; a crashed worker can later return success for an obsolete attempt. Persist a parent run with explicit states, attempt fencing, child associations, and atomic terminal transitions. Recheck local eligibility before publishing aggregate success, and bound the age difference between evidence for the first and last requirement. **Existing coverage:** Connect Links use atomic claims, pin provisioned service IDs, and recover stale claims. Their code explicitly acknowledges duplicate provisioning if a process dies after creation but before pinning. That limitation must not silently become “exactly once onboarding.” See [completion claim and crash window](<backend/src/services/connect_link_service.rs:323>).

22. **A validator can destroy a healthy OAuth connection by racing refresh.** A probe using an old access token may return 401 while the sweep successfully refreshes it. Independently spending a rotating refresh token can invalidate the winner; a stale validation failure can overwrite a fresh authorization. Use the existing coordinated refresh path, then validate the returned current credential and discard superseded results. Do not translate every timeout, 429, or 5xx into permanent credential failure. **Existing coverage:** refresh uses per-key Mongo leases, revision comparisons, and compare-and-set writes; the sweep distinguishes provider failures from transient failures. It only covers a defined subset of OAuth rows, so it cannot certify API keys or every legacy connection. See [refresh coordination](<backend/src/services/user_token_service.rs:2221>) and [sweep coverage](<backend/src/services/user_token_service.rs:2670>).

23. **A successful check becomes stale before the callback, and `credential_epoch` is insufficient as a health version.** The provider can revoke access immediately after success; an org can revoke membership; a node can disconnect. Epochs invalidate user replacements, but intentionally do not advance on refresh, which can still update recorded scopes. `last_used_at` is also unsuitable as proof: refresh writes it. Evidence needs its own checked time, validation profile/version, credential identity/epoch, relevant configuration and permission dependencies, and an expiry policy. **Existing coverage:** exact approvals bind authority and revalidate before effect. They do not promise future upstream availability. Define success as bounded evidence and keep normal execution checks authoritative. See [freshness semantics](<docs/GRANULAR_APPROVALS_DESIGN.md:351>) and [refresh field updates](<backend/src/services/user_token_service.rs:2584>).

24. **Disabled services, deleted tombstones, and missing credentials can masquerade as satisfied requirements.** `GET /keys` includes disabled services whose credential status may remain active. Delete retains a service tombstone while removing its endpoint and credential. Slugs can also be reused among active rows, so remembering only a slug can select a different connection later. Never auto-enable or recreate a connection merely to make onboarding green. **Existing coverage:** active-only listings, UUID-based management, `credential_missing`, and documented lifecycle rules already distinguish these cases. The architecture document also records zombie/tombstone edge cases, reinforcing the need to validate the complete relationship. See [service lifecycle and listing contract](<docs/AI_SERVICES_ARCHITECTURE.md:153>).

25. **“Return to the same link later” conflicts with Connect Link terminal semantics.** Existing links are single-use, normally last 15 minutes, and stop accepting completion after terminal status. Reopening completed links would make historical callbacks, webhook events, and MCP activation ambiguous. Making their bearer tokens permanent would extend exposure. Separate the stable app entry URL from bounded onboarding runs and single-service Connect Links; a new visit evaluates current requirements and current evidence without rewriting old outcomes. **Existing coverage:** explicit terminal states, expiry, and finalization grace already provide useful child-flow behavior. Preserve that behavior rather than changing `completed` into a mutable readiness flag. See [Hosted Connect Link contract](<CLAUDE.md:180>) and [link states](<backend/src/models/connect_link.rs:11>).

26. **“Failure callback” cannot be guaranteed when the user abandons the browser.** Closing a tab produces no reliable redirect. Provider denial may be retryable; app-consent denial is an explicit decision; expiration is different from temporary validation failure; partial completion does not justify deleting newly connected services. Define these outcomes separately and make callback delivery a notification mechanism. Apps need an authoritative status path and an abandonment/expiry policy. **Existing coverage:** Connect Links distinguish completed/cancelled/expired, retain retryable provider errors, and sweep abandoned app links for expiry events. SDK polling timeout is already separate from server expiry. See [Connect Link lifecycle rules](<CLAUDE.md:184>) and [SDK wait outcomes](<sdk/oauth-core/src/services.ts:342>).

27. **Webhooks are neither exactly-once delivery nor a complete readiness subscription.** Duplicate, late, reordered, and exhausted deliveries must not reverse newer state. More fundamentally, `connection.expired` resolves one service and targets its `source_app_id`; a pre-existing GitHub connection reused by CMA, heca, and Aevatar is not a subscription relationship to all three. **Existing coverage:** terminal Connect Link events have a bounded durable outbox; connection-expiry side effects are best effort. Delivery uses timestamped HMAC, and the SDK verifies signatures and freshness, but receivers still need event-ID deduplication and authoritative status reconciliation. Any ongoing readiness-notification feature needs explicit consumer relationships and revocation rules. See [expiry recipient selection](<backend/src/services/connection_expiry_service.rs:184>), [delivery contract](<CLAUDE.md:193>), and [SDK verification](<sdk/oauth-core/src/webhooks.ts:20>).

28. **Automatic services and private app access can create circular onboarding dependencies.** An ORNN-like service may use identity forwarding or platform credentials and require no user OAuth connection. Some private services become eligible only after consent to an associated developer app. Requiring that service to exist before consent can deadlock; granting everything first can issue excessive authority before requirements are satisfied. If app requirements can recursively name other apps, cycles need explicit treatment. **Existing coverage:** no-auth auto-provisioning checks category, credential requirements, private visibility, and valid app consent, while preserving existing inactive rows. The new flow must choose a sequencing model that respects those gates. See [auto-provisioning eligibility](<backend/src/services/unified_key_service.rs:1623>).

29. **Inserting onboarding into OAuth can break protocol timing and existing clients.** A previously consented user can currently bypass the consent UI; `prompt=none` must not suddenly launch a connection wizard. Issuing the authorization code before a long setup flow risks expiration, while issuing unrestricted tokens early defeats a hard readiness gate. Decide whether this is an explicitly requested OAuth extension, a separate flow after login, or both, and bind that choice to server-authoritative inputs. **Existing coverage:** authorization handles forced login/consent and noninteractive errors; signed consent requests last 15 minutes and authorization codes five minutes. A resumable onboarding session must not simply stretch or replay those artifacts. See [authorization flow](<backend/src/handlers/oauth.rs:903>), [consent lifetime](<backend/src/handlers/oauth.rs:304>), and [authorization-code lifetime](<backend/src/services/oauth_service.rs:85>).

30. **A browser-only implementation leaves CLI, MCP, and SDK consumers with incompatible meanings of success.** Headless callers need a URL/code handoff, authenticated status polling, resumable identifiers, and explicit cancellation; a fully offline caller cannot receive live validation guarantees. Existing MCP waiting activates service tools once a Connect Link is completed, which currently means provisioning. The OAuth SDK exposes neither resource parameters nor onboarding requirements in its login options and stores one pending OAuth state per client ID, so nested or concurrent flows need deliberate handling. **Existing coverage:** `nyx__connect_service`, bounded `nyx__wait_for_connection`, SDK Connect Link orchestration, and first-party device login are useful primitives. Preserve their current contracts and expose readiness separately and consistently. See [MCP connection handoff](<backend/src/services/mcp_service.rs:4554>), [MCP completion activation](<backend/src/handlers/mcp_transport.rs:2460>), and [SDK authorization state](<sdk/oauth-core/src/index.ts:127>).

I’ll stop here and wait for the draft plan.
