BLOCKED

# Adversarial Review: Direct Chrono-LLM Plan

Reviewed against Draft v3, the implementation plan, the current `chat-chronollm-direct` worktree, and the historical transport named by FE-1. The production facts declared trusted in spec section 0b were not re-litigated. The plan is blocked by incorrect billing, a transport-selection design that cannot perform the promised runtime switch, and missing ownership/reset semantics for browser-resident transcripts.

## BLOCKER

### BLOCKER 1: `chrono-llm-public` does not enter the reported-usage billing path

- **Claim attacked:** Spec section 7 says forced `stream_options.include_usage` makes streamed direct turns bill on reported tokens rather than byte estimates (`docs/chat/direct-chronollm-spec.md:288-290`); the plan treats this as structurally solved (`docs/chat/direct-chronollm-impl-plan.md:108-110`).
- **Evidence:** The assistant router does carry `BillingRoutePolicy::Metered(BillingIngress::Proxy)` (`backend/src/routes.rs:1313-1341`), and proxy egress fails closed without that extension (`backend/src/handlers/proxy.rs:1344-1346`). The defect is later: SSE usage observation is enabled only when `target.service.slug.starts_with("llm-")` (`backend/src/handlers/proxy.rs:2635-2649`). `chrono-llm-public` therefore takes the generic streaming branch; because SSE is not JSON, that branch leaves `stream_usage_context` absent (`backend/src/handlers/proxy.rs:2865-2886`) and settles with `reported_usage = None` (`backend/src/handlers/proxy.rs:2928-2949`). The row's explicit `platform_metric` still classifies it as token-metered (`backend/src/handlers/proxy.rs:3135-3154`), but absent reported usage is converted to a byte estimate (`backend/src/handlers/proxy.rs:3180-3187`; `backend/src/services/llm_usage_service.rs:250-261`). Thus `include_usage` can be present and parsed by nobody.
- **Concrete fix:** Make usage capture depend on the effective token billing metric plus a supported response shape, not a service-slug prefix, or explicitly mark/allow `chrono-llm-public` as an OpenAI SSE usage source. Add a route-level test through the real assistant POST boundary that emits the saved usage frame and proves the settled billing quantity equals the reported total, with provenance showing reported rather than estimated usage.

### BLOCKER 2: `DelegatingAssistantTransport.install()` cannot implement the promised reactive engine switch

- **Claim attacked:** FE-2 says `useFeature(...)` will switch engines through `DelegatingAssistantTransport.install()`, re-evaluate on every flag change, preserve mock/test behavior, and leave an in-flight turn on its original transport (`docs/chat/direct-chronollm-impl-plan.md:74-80`; `docs/chat/direct-chronollm-spec.md:230-243`).
- **Evidence:** `install()` is deliberately one-shot: after the first call, `interceptorInstalled` permanently makes later calls return `false` (`frontend/src/lib/assistant/transport.ts:571-588`). In development, that single slot is already owned by the scenario interceptor (`frontend/src/lib/assistant/transport.ts:709-719`; `frontend/src/lib/assistant/scenario-intercept-transport.ts:837-843`). The singleton is constructed once at module evaluation and exported as the narrower `AssistantTransport` interface, which does not expose `install()` at all (`frontend/src/lib/assistant/transport.ts:722-774`; `frontend/src/types/assistant.ts:282-339`). Test/mock mode returns a non-delegating mock directly (`frontend/src/lib/assistant/transport.ts:731-741`). The flag itself is reactive and does refresh: `useFeature` reads the auth-store capability (`frontend/src/hooks/use-feature-flag.ts:17-22`), and `/users/me` polls every 60 seconds (`frontend/src/hooks/use-auth.ts:15-31`), but there is no compatible mutable engine selector for that value to drive.
- **Concrete fix:** Replace the proposed use of `install()` with a permanent engine-router transport that owns both Aevatar and direct delegates, has an explicit selected-engine state, routes conversation-scoped calls by validated ID prefix, and snapshots/registers the delegate for each running turn. Keep the scenario interceptor as an outer wrapper instead of competing for the engine slot. Specify initialization and behavior for production, development, `?mock`, and Vitest before implementation.

### BLOCKER 3: the resurrected in-memory store can expose one user's transcript to the next user in the same tab

- **Claim attacked:** The direct mode is described as browser-memory-only and reset on reload (`docs/chat/direct-chronollm-spec.md:76-78`, `docs/chat/direct-chronollm-spec.md:255-256`), but neither the spec nor FE-1 defines an ownership boundary or logout reset.
- **Evidence:** The historical implementation to be resurrected stores every transcript in an instance-wide `Map` and returns the entire map from `listConversations` (`e3c2f36e^:frontend/src/lib/assistant/completions-transport.ts:80-110`). The transport singleton survives logout (`frontend/src/lib/assistant/transport.ts:744-774`). Auth cleanup clears context, draft, and wire-log stores, but not any assistant transport (`frontend/src/stores/auth-store.ts:14-18`, `frontend/src/stores/auth-store.ts:84-98`, `frontend/src/stores/auth-store.ts:110-127`); explicit logout clears React Query only (`frontend/src/hooks/use-auth.ts:66-77`). `resetAssistantTransport` resets only `MockAssistantTransport` (`frontend/src/lib/assistant/transport.ts:776-779`). A logout followed by a different login in the same SPA lifetime can therefore render the previous user's local direct conversations.
- **Concrete fix:** User-scope the direct store or give it an explicit `reset/abortAll` lifecycle invoked on every identity transition, including explicit logout, session-invalidating 401, `setUser(null)`, and user A to user B without reload. Clear direct conversation queries at the same boundary. Add a single-module-lifetime test for `null -> user A -> transcript -> logout -> user B` proving no list, history, running request, picker state, or draft survives.

## MAJOR

### MAJOR 1: engine-agnostic query and cancellation state defeats the prefix and close-over safety claims

- **Claim attacked:** The spec says a mid-session flip cannot route work to the wrong engine, a running turn keeps its original transport, and direct mode hides/does not fetch Aevatar history (`docs/chat/direct-chronollm-spec.md:237-243`).
- **Evidence:** Every assistant query key is engine-agnostic (`frontend/src/hooks/use-assistant.ts:35-45`), and list/history queries invoke the mutable singleton under those unchanged keys (`frontend/src/hooks/use-assistant.ts:344-358`). The assistant page mounts those queries unconditionally (`frontend/src/pages/assistant.tsx:144-193`), so changing a delegate neither hides nor refetches the old engine's state. `pendingCreate` is also one module-global promise with no engine stamp (`frontend/src/hooks/use-assistant.ts:460-474`). More seriously, both the stream-start timeout and the user's Stop action call `assistantTransport.cancelActiveTurn(...)` on whichever delegate is current at cancellation time (`frontend/src/hooks/use-assistant.ts:640-655`, `frontend/src/hooks/use-assistant.ts:816-827`), not the handle/delegate that started the turn.
- **Concrete fix:** Include engine identity in conversation/history/turn/episode/workspace query keys; remove or invalidate the prior engine's cache and draft URL state on a flip; engine-stamp `pendingCreate`; and route all ID-scoped operations, especially cancellation, through a prefix-aware router or running-turn registry. Add tests for cache separation, no Aevatar fetch while direct is selected, pending-create during a flip, and Stop/start-timeout after a mid-stream flip.

### MAJOR 2: the historical parser terminates before the trusted usage frame and violates the stated EOF contract

- **Claim attacked:** FE-1 proposes resurrecting the old transport and adapting its chunk handling for `finish_reason`, the usage frame, `[DONE]`, and EOF-without-terminal failure (`docs/chat/direct-chronollm-spec.md:247-254`, `docs/chat/direct-chronollm-spec.md:272-278`).
- **Evidence:** The historical reader returns as soon as `run.finished` becomes true (`e3c2f36e^:frontend/src/lib/assistant/completions-transport.ts:267-276`), while `finish_reason` immediately calls `finishTurn` (`e3c2f36e^:frontend/src/lib/assistant/completions-transport.ts:321-355`). It also treats bare EOF as successful completion (`e3c2f36e^:frontend/src/lib/assistant/completions-transport.ts:278-282`). In the saved stream, finish is at `frontend/src/lib/assistant/__fixtures__/chrono-llm-direct-stream.sse:21`, usage at line 23, and `[DONE]` at line 25. Dropping the browser response can cancel the backend response stream and upstream body (`backend/src/downstream_disconnect.rs:75-106`), potentially before a separately delivered usage frame is observed. The old class is also no longer structurally compatible with the expanded transport contract (`frontend/src/types/assistant.ts:282-339`).
- **Concrete fix:** Separate UI terminal state from stream-drain state: record `finish_reason`, close the visible message, continue reading through usage and `[DONE]`/EOF, and only then release the reader. EOF succeeds only if a valid terminal marker was observed. Implement explicit direct-mode behavior for every current projection, delete, cancellation, approval, and action method. Tests must prove the usage frame is consumed, EOF after a valid finish succeeds, EOF before any terminal marker fails, and abort settles exactly once.

### MAJOR 3: authoritative feature gating adds at least two uncached MongoDB operations to every direct turn

- **Claim attacked:** BE-3 says to reuse `/users/me` effective-feature resolution on every direct handler (`docs/chat/direct-chronollm-impl-plan.md:52-54`) without accounting for hot-path cost.
- **Evidence:** The correct function is `resolve_personal_features`; its pure grant-union semantics match the spec (`backend/src/services/feature_flag_service.rs:303-333`). Its async wrapper first queries active org memberships (`backend/src/services/feature_flag_service.rs:352-356`; the query is at `backend/src/services/org_service.rs:860-876`) and then queries all applicable override rows (`backend/src/services/feature_flag_service.rs:358-371`). There is no cache. Existing assistant code explicitly checks a cheap header before resolving a flag because flag resolution performs MongoDB I/O and should not burden normal turns (`backend/src/handlers/assistant.rs:159-168`). With billing enabled, `BillingService::open` can independently perform feature resolution again for billing rollout (`backend/src/services/billing/mod.rs:158-168`).
- **Concrete fix:** Keep backend authority and grant-union behavior, but add an explicit cost decision to the plan: preferably a short, bounded, invalidation-aware effective-feature cache shared with `/users/me`, or a purpose-built boolean resolver/cache for this flag. Document rollout latency and failure behavior, and add a query-count/cache invalidation test; do not silently accept two additional Mongo reads per streamed turn.

### MAJOR 4: the claimed per-user rate limit does not exist for this human-only paid route

- **Claim attacked:** Spec section 7 says “standard per-user middleware” rate-limits the new endpoint (`docs/chat/direct-chronollm-spec.md:286-287`).
- **Evidence:** Global middleware checks a client-IP bucket and a global fallback, not user identity (`backend/src/mw/rate_limit.rs:562-611`; mounted at `backend/src/main.rs:1101-1109`). `execute_admin_proxy` also calls the per-agent limiter (`backend/src/handlers/proxy.rs:1349-1368`), but that limiter is active only when `AuthUser.api_key_id` and an API-key rate are present (`backend/src/mw/rate_limit.rs:370-404`). The assistant router rejects API keys, service accounts, delegated tokens, and relay tokens (`backend/src/routes.rs:1351-1353`, `backend/src/routes.rs:1403-1406`), so human direct-chat calls receive no per-user control. This is a platform-master-credential, cost-bearing endpoint with transcript resend growth.
- **Concrete fix:** Add a dedicated authenticated-user limiter for direct completions, preferably including a small per-user in-flight cap. Keep cheap skills/models discovery on a separate policy. Specify 429 behavior and add tests proving limits are isolated by user and cannot be bypassed by concurrent streams from one account.

### MAJOR 5: assistant forwarding routes are outside the billing route inventory and its real-boundary smoke test

- **Claim attacked:** The plan assumes mounting inside `assistant_proxy_routes` is enough for billing coverage (`docs/chat/direct-chronollm-impl-plan.md:55-56`; `docs/chat/direct-chronollm-spec.md:288-291`).
- **Evidence:** The current shared route layer does provide a runtime proxy billing extension (`backend/src/routes.rs:1313-1341`), so this is not the same defect as BLOCKER 1. However, the formal billing inventory contains LLM, proxy, MCP, SSH, public, and Oracle routes but no assistant route (`backend/src/services/billing/route_inventory.rs:97-240`). `mounted_billing_route_inventory()` is generated only from those route macros (`backend/src/routes.rs:330-343`), and the equality/real-boundary tests compare only that generated subset (`backend/src/billing_integration_tests.rs:1857-1865`, `backend/src/billing_integration_tests.rs:1927-1938`). A direct assistant POST can therefore be omitted from the layer, or added after Axum's `route_layer` call, without the billing coverage gate noticing.
- **Concrete fix:** Register the new POST through a billing-route macro/inventory entry and exercise its real authenticated assistant boundary in the billing smoke suite. Apply the metered `route_layer` only after all forwarding routes are registered. Leave skills/models outside that forwarding layer or explicitly inventory them as control-plane exemptions.

### MAJOR 6: BE-4 removes an explicitly retained public contract; repository grep cannot establish external deadness

- **Claim attacked:** BE-4 calls `POST /api/v1/assistant/completions` dead and says FE/CLI/docs grep was clean (`docs/chat/direct-chronollm-impl-plan.md:58-62`; `docs/chat/direct-chronollm-spec.md:134-138`).
- **Evidence:** Runtime repository search finds no frontend, CLI, or wizard caller, and the deployed wizard manifest contains no assistant page/transport (`cli/src/wizard/bundle-meta/index.manifest:55-90`). But the canonical assistant wire reference explicitly lists `POST /completions` and says it is a retained backend surface (`docs/chat/02-wire-contract.md:1-5`, `docs/chat/02-wire-contract.md:23-37`). The live route and handler still document the same API (`backend/src/routes.rs:1330`; `backend/src/handlers/assistant.rs:956-973`). An internal grep cannot disprove external callers to a published HTTP route.
- **Concrete fix:** Drop BE-4 unless API removal is separately approved with a deprecation/removal policy. If removal is intentional, update the canonical wire contract and release notes, state the external compatibility risk explicitly, and add a deliberate route-absence test; do not present repository call-site absence as proof of API deadness.

### MAJOR 7: preserving the session on 401 is wrong for skills/models and underspecified for completions

- **Claim attacked:** FE-1 and spec section 5.2 require `preserveSessionOn401` for the direct JSON GETs and say direct-mode calls must never clear NyxID auth (`docs/chat/direct-chronollm-impl-plan.md:67-72`; `docs/chat/direct-chronollm-spec.md:257-263`).
- **Evidence:** The API client states that `preserveSessionOn401` is for downstream integrations and “Requests that authenticate against NyxID itself must NOT set this” (`frontend/src/lib/api-client.ts:29-37`). Skills and models are NyxID handlers with `AuthUser`, not downstream calls, so their 401 means the NyxID session is invalid and should clear auth. The convenience `api.get` does not accept request options anyway (`frontend/src/lib/api-client.ts:157-160`). The raw completions POST is ambiguous: a NyxID middleware/handler 401 and a proxied upstream 401 share the HTTP status, but NyxID's structured error includes `error_code`; existing stream-start parsing already recognizes NyxID `{error,error_code,message}` versus upstream `{code,message}` shapes, although it currently treats every 401/403 as downstream (`frontend/src/lib/assistant/aevatar-transport.ts:1097-1145`).
- **Concrete fix:** Use normal `api.get` behavior for skills/models. For raw completions, parse the pre-SSE JSON envelope and clear auth only for a NyxID authentication error (for example error code 1001/token expiry), while preserving the session and showing reconnect copy for a genuine downstream 401/403. Add distinct tests for invalid NyxID session, upstream rejection, flag-off 404, and non-JSON upstream failure.

## MINOR

### MINOR 1: the 256 KiB request cap has no unambiguous unit or wire-limit design

- **Claim attacked:** The spec permits 32,768 “chars” per message and 256 KiB total (`docs/chat/direct-chronollm-spec.md:153-157`), while BE-2 only names a validation function (`docs/chat/direct-chronollm-impl-plan.md:38-40`).
- **Evidence:** The application installs a 1 MiB default body limit (`backend/src/main.rs:1084-1089`), while existing assistant handlers explicitly read raw bodies with their own 256 KiB cap and map overflow to `BadRequest` (`backend/src/handlers/assistant.rs:975-994`). A decoded-content cap is not a wire cap: JSON escaping and multibyte UTF-8 can make a valid 256 KiB transcript materially larger on the wire. The spec does not say whether “chars” means Unicode scalar values and whether total means UTF-8 bytes, scalar count, or raw JSON bytes.
- **Concrete fix:** Define all three limits separately: raw request bytes, per-message Unicode scalar count, and decoded aggregate UTF-8 bytes. Read the body with an explicit bounded `to_bytes`, then deserialize and validate. Add boundary tests for multibyte text, escape-heavy strings, exact limits, and raw-body overflow; choose and document whether overflow is the existing 400/1000 convention or a new 413 taxonomy.

### MINOR 2: the proposed embedded skills are small enough, but their operative instructions conflict with direct mode

- **Claim attacked:** The plan proposes embedding the existing NyxID, GitHub-via-NyxID, and Firecrawl-via-NyxID skills while promising a no-tools/no-actions chat mode (`docs/chat/direct-chronollm-impl-plan.md:35-37`; `docs/chat/direct-chronollm-spec.md:79-83`, `docs/chat/direct-chronollm-spec.md:267-270`).
- **Evidence:** All files exist and fit the 64 KiB cap: `skills/nyxid/SKILL.md` is 16,356 bytes, `skills/github-via-nyxid/SKILL.md` is 11,225 bytes, and `skills/firecrawl-via-nyxid/SKILL.md` is 10,400 bytes. But they instruct the model to use the CLI or agent tools and perform operations: `skills/nyxid/SKILL.md:31-47`, `skills/nyxid/SKILL.md:138-149`; `skills/github-via-nyxid/SKILL.md:19-35`, `skills/github-via-nyxid/SKILL.md:127-143`; `skills/firecrawl-via-nyxid/SKILL.md:40-60`, `skills/firecrawl-via-nyxid/SKILL.md:80-114`. Because the skill body is concatenated into the same system message after the base prompt, it is not lower-priority reference material.
- **Concrete fix:** Embed condensed informational variants written for advisory-only direct chat, or append an explicit server-owned suffix that overrides every action/tool instruction and requires the model to describe user-executable steps without claiming execution. Add a prompt-shape test that pins this constraint for every included skill.

## Verified High-Risk Claims

- `execute_admin_proxy` has the planned call shape, including `Request<Body>`, empty extra-header vector, and mutable `resolved_slug` output (`backend/src/handlers/proxy.rs:999-1026`); the existing assistant call demonstrates it (`backend/src/handlers/assistant.rs:691-710`).
- Direct SSE passthrough is genuinely streaming, detects SSE case-insensitively, and strips stale `content-length` (`backend/src/handlers/proxy.rs:2622-2676`, `backend/src/handlers/proxy.rs:3370-3386`).
- Generalizing `resolve_admin_service` by slug can preserve Aevatar behavior, and both service and proxy target resolution enforce active/platform and `requires_user_credential` guards (`backend/src/services/assistant_service.rs:30-60`; `backend/src/services/proxy_service.rs:434-470`).
- The private API's cookie-authenticated POSTs are covered by global Origin/Referer CSRF enforcement (`backend/src/main.rs:1067-1071`; `backend/src/mw/csrf.rs:80-130`), and the human-only assistant nest rejects API-key, service-account, delegated, and relay tokens (`backend/src/routes.rs:1351-1353`, `backend/src/routes.rs:1403-1406`).
- Grant-union semantics fit the requested flag behavior (`backend/src/services/feature_flag_service.rs:303-333`). `AppError::NotFound` mechanically produces HTTP 404 with code 1003 (`backend/src/errors/mod.rs:456-466`, `backend/src/errors/mod.rs:586-594`); no conflicting backend gate was found, although the plan's “same posture as other gated surfaces” claim has no concrete server-side precedent in this tree.
