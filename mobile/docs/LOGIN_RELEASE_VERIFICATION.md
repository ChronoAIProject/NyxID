# Login compatibility release verification

The app supports account-login codes such as `ABCD-EFGH` and v2 device-login
codes such as `2-ABCD-EFGH`. A leading `2` is part of the request identity when
the normalized code has nine characters. An eight-character code beginning
with `2`, such as `2ABC-DEFG`, is still a legacy request.

The code formatter preserves extra characters so an invalid paste stays
invalid. Native text fields must not truncate a pasted value to a valid code;
the complete normalized value is validated before requesting a preview.

## Prepare the candidate

Use the existing production configuration and signing identity described in
[the mobile README](../README.md#environment). In particular, set
`PROD_FRONTEND_URL` to the origin that serves the login QR, independently of
the API and legal-document origins. Confirm the next iOS build number against
App Store Connect before building; historical numbers in documentation are
not a release source of truth.

Run from `mobile/`:

```sh
pnpm install --frozen-lockfile
pnpm test
pnpm typecheck
pnpm check:native-sync
pnpm build:ios
```

Record the Git revision, marketing version, iOS build number, configured API
and frontend origins, and exported IPA checksum with the release evidence.
`build:ios` exports an IPA locally; `submit:ios` uploads it to TestFlight.
Review the candidate and validation results before submission or publication.

## Verify on iPhone

Use fresh requests generated by the corresponding browser or CLI. The
example codes below describe formats; they are not live requests.

| Scenario | Expected behavior |
| --- | --- |
| Scan a web account-login QR (`ABCD-EFGH`) | Request details load; approval signs the requesting browser in. |
| Scan a v2 CLI QR (`2-ABCD-EFGH`) | The entire code reaches preview; the user can review the supported grant choices. |
| Type and paste both formats in the main field and scanner's manual-entry sheet | No final character is lost; Continue requests the matching preview. |
| Type, delete, and re-enter the final character | The completed code still identifies the original request. |
| Enter a legacy code beginning with `2` | It remains a legacy request until a valid nine-character v2 code is entered. |
| Paste an extra character after a complete code | The extra character remains visible; the invalid code cannot be submitted. |
| Open a trusted login deep link with an overlong code | It cannot be shortened into a request that can be approved. |
| Scan an untrusted-origin QR, malformed code, or duplicate `user_code` | The scanner rejects it before a preview request. |
| Approve or reject expired/already completed requests | No second approval is issued; the app shows the appropriate terminal/error state. |
| Review a v2 restricted-key request | Only the explicitly selected grant is delivered; an account session is not delivered alongside it. |

Also smoke-test Agent Key manual entry and Android, because they use the same
formatter. Record device model, iOS version, installed build, and results.
Unit/type checks and an Expo bundle export do not verify native keyboard,
paste, camera, signing, or installed-app behavior.

Browser-to-app launch and return guidance are a separate feature. This
compatibility change does not add automatic preview, Universal Link routing,
or a biometric approval step.
