# Native integration and device verification (#1868, Workstream 3)

This work supports the Expo 55 / React Native 0.83 iOS and Android apps. Automated checks exercise protocol, persistence, lifecycle and configuration boundaries. The PM owns verification on physical devices and records device/OS/build, provider, backend revision, configuration and observed result. No device verification is claimed by the implementation tests; recorded results are in [NATIVE_VALIDATION_2026-11-14.md](NATIVE_VALIDATION_2026-11-14.md).

## Host decision and rollout

The owner still chooses A (API plus frontend hosts) or B (API hosts only). This change retains today's iOS associated domains, AASA paths and OneLink host/path. `buildNativeLinks.associatedUrls` is the single native association host input; it currently receives both embedded API URLs for option B. Selecting A changes only that input to include the embedded frontend URLs. The same shared path manifest and generator apply to either host set, covered by tests. React Native routing prefixes continue to include both trusted API and frontend origins independently of the OS-associated host choice, so received-link routing code does not change. Browser fallback trusts embedded API/frontend origins independently of which hosts the OS associates. AASA and Asset Links responses are host independent; the deployment owner serves the same endpoint responses on each chosen origin, without redirects. No host decision changes native route code.

Platform/deployment owner rollout order:

1. Confirm the released iOS bundle id and Android package for each environment. Keep the existing OneLink host and prefix. Obtain the owner's A/B decision before changing associated domains or host inputs.
2. Deploy the new backend to all replicas. Both migration API hosts must serve the association files over public HTTPS without auth, redirects or HTML interception. For A, the frontend edge must also serve/proxy the same well-known files. AASA paths remain exactly the shared manifest.
3. Validate both well-known responses from every chosen host and their identity values. Check CDN headers and content type; allow cache propagation. Test OneLink independently.
4. Only after **every** selected association host serves valid Asset Links, set the chosen profile's `*_ANDROID_HTTPS_APP_LINKS=true`, rebuild and distribute it. This flag is profile-local and never inherits dev's opt-in into production. Default false preserves exactly the previous Android filters. Pre-Android-12 verification is all-or-nothing across hosts, so enabling prematurely can break OneLink too.
5. Device owner verifies both embedded domain sets and the chosen host set. Keep both API origins reachable during the domain migration overlap. Disabling the build flag requires a rebuilt Android app; server association-file rollback alone does not remove installed filters.

## Push configuration (platform and deployment owners)

For iOS, the Apple Developer owner enables Push Notifications for the exact bundle id and provisions the app with `aps-environment`. Create an APNs signing `.p8` key and configure backend `APNS_KEY_PATH`, `APNS_KEY_ID`, `APNS_TEAM_ID` and `APNS_TOPIC` (the app bundle id). `APNS_SANDBOX=true` is for development provisioning; TestFlight/App Store use production (`false`). Install the key through deployment secrets, never source control. The AASA `appID` is `APNS_TEAM_ID.APNS_TOPIC`; APNs identity is also used when no push key has been installed. Verify `/.well-known/apple-app-site-association` on each associated host.

For Android, the Firebase owner creates the Android app with the exact `*_ANDROID_PACKAGE`, downloads its `google-services.json`, and selects it through `*_GOOGLE_SERVICES_FILE`. The existing build validation checks package match. The deployment owner provides backend `FCM_SERVICE_ACCOUNT_PATH` for a Firebase service account in that same project with FCM send permission. This private server credential differs from the app's Firebase config and from the Play submission service account. Use real builds/devices with notification permission; Expo Go/native modules without token support cannot prove delivery.

Verify request, approval decision, machine and NyxBot notifications foregrounded, backgrounded and after termination. Tap cold and warm notifications with navigation guards active. Log out while the network is unavailable: tray/badge must clear, native unregistration is attempted, and token refresh while signed out must cause no NyxID request. Push server operations remain serialized, but logout waits at most ten seconds for its queued unbind. If that budget expires, it unregisters natively, retains the known token for a later account rebind, and lets sign-out continue; late completions cannot overwrite recovery state. Native token acquisition times out after 15 seconds as unavailable. Runtime handlers and listeners install after hydration without waiting for the push queue. Native unregistration is the first layer when that unbind fails. Each attempt is bounded to two seconds, with up to three attempts and 100/200 ms backoff; unsuccessful cleanup retries on the next launch, active transition or connectivity recovery even while signed out. The app keeps only a SecureStore pending-unbind record (`token`, provider, platform and creation time, plus a retry flag if native unregistration failed), retains no credentials or account tokens, and suppresses presentation in the app as a second layer. While the record exists, the next login/launch/active/connectivity retry first POSTs that stored token to the authenticated account. It does not fetch a native token before this rebind. After the rebind succeeds, the record is cleared and the native token is fetched: the same token completes with no second server call, while a changed token rotates with the stored token as `previous_token`. Network/timeouts, HTTP 401/408/429 and 5xx rebind failures make no native registration call, keep the record and retry on the next launch, active transition or connectivity recovery. Other 4xx responses discard the record and immediately attempt normal registration; records older than seven days (the refresh-token lifetime) also give up and use normal registration. Foreground notification presentation, in-app toasts and notification taps are suppressed while the record remains, although silent signed-in refresh signals may still update data. Until native unregistration succeeds, the OS may still show the previous account’s pushes while the app is backgrounded or killed; in-app suppression covers only the foreground and taps. Log into another account, including a run where the OS returns the same token; verify the server binding moves and no stale tap opens the previous account's work. The contract tests use the payload keys emitted by `notification_service.rs` and `assistant_notification_service.rs` (`type`, `challenge_id`/`request_id`, `url`/`deeplink`, `notification_id`).

## Android association identity (Android release owner)

Set backend `ANDROID_APP_PACKAGE` and `ANDROID_APP_SHA256_CERT_FINGERPRINTS`. In Play Console → App integrity → App signing, copy the **App signing key certificate SHA-256**, which signs Play-distributed installs. Also record the **Upload key certificate SHA-256** and include it only when testing directly installed APKs signed with that key. Obtain local certificates with `keytool -list -v -keystore <keystore>`; for debug builds include the debug signing certificate only in the intended environment. Comma-separate the full colon-delimited 32-byte fingerprints. Key rotation may require both old and new signing certificates during overlap. The endpoint normalizes uppercase and rejects malformed configuration at startup.

After deployment, verify `https://<each-host>/.well-known/assetlinks.json` has relation `delegate_permission/common.handle_all_urls`, namespace `android_app`, the exact package and signing fingerprints. Enable the build opt-in only after those checks. On Android 12+, use `adb shell pm verify-app-links --re-verify <package>` and `adb shell pm get-app-links <package>`. Exercise an older supported Android version too. Use `adb shell am start -a android.intent.action.VIEW -d 'https://<host>/login/device?user_code=…'` to verify dispatch without approving automatically. On iOS, install a signed build, tap the same claimed paths from another app, and verify AASA identity through the Apple associated-domains diagnostics. Custom-scheme device and Agent Key links must remain supported.

## Service OAuth (provider administrators)

The auth session requests ephemeral isolation on iOS (no Safari cookie sharing), matching the previous in-app browser; Android ignores this option.

Register `{BASE_URL}/api/v1/providers/callback` in each provider application's redirect allowlist. During domain migration register the corresponding callback on **both** API origins before enabling the mobile domain flag. The callback goes to NyxID first; do not register `nyxid://services/oauth-return` with the provider. NyxID validates and persists only the exact `<scheme>://services/oauth-return` app destination and appends only `status=success|error` and a fixed normalized error `code`. It never returns credentials, state, nonce or provider text. `nyxid` is always allowed. Builds with a custom `APP_SCHEME` require the same lowercase scheme in backend `MOBILE_APP_RETURN_SCHEMES` on every replica; without that configuration, initiate falls back to the server-state flow after a 400 and no automatic app return is expected. `exp://` is never accepted for service OAuth. Social login uses its own exact callback configuration in `MOBILE_SOCIAL_REDIRECT_URIS`. `app_return_uri` is incompatible with `redirect_path` and completion-page flows `cc`/`wz`.

All `provider_type=oauth2` providers pass through `user_token_service::initiate_oauth_connect` and use the generic callback without exceptions, including admin-created providers. The code constructs the callback unconditionally from `BASE_URL`; a provider's device `hosted_callback_url` does not override the authorization-code callback.

| Seeded OAuth provider(s) | Callback / native verification |
| --- | --- |
| ifttt-mcp; cloudflare; supabase-management; railway | Generic callback. Configure the provider's platform/BYO app; IFTTT retains its existing MCP scope policy. |
| twitter; google; github; facebook; discord; spotify; linkedin; slack; microsoft; tiktok; twitch; reddit; lark; feishu | Generic callback. Provider permissions, app approval and region remain provider-owned. |
| posthog; posthog-eu; notion; google-cloud | Generic callback. Google Cloud/BYO clients still need prior web configuration when unavailable on mobile. |
| stripe; airtable; asana; attio; bitbucket; box; calendly; capsule-crm; clickup; crowdin; dialpad; dropbox; eventbrite; figma; gitlab; hubspot; intercom; jira; linear; miro; pagerduty; productboard; sentry; shippo; square; todoist; zoom | Managed OAuth seed registry; same generic callback. |
| Device-code providers (including OpenAI/Codex), API-key providers and Telegram widget | Existing specialized setup/native credential form or explicit web handoff. This change adds no new device-code or API-key protocol. |

For **each configured OAuth provider**, the PM verifies a new connection and a reconnect, successful authorization, denial, provider error and browser cancellation on iOS and Android. Also test a browser signed into another NyxID account, app background/resume, force-kill/relaunch within ten minutes, expiry, logout and account switch. Confirm the connection only reports success when the server is active and authorization differs from the saved baseline. A success return with unchanged server state must offer Check again. Cancellation must offer Continue authorization and Check again; Continue creates a new state for the same connection. One delayed recheck (500 ms) bounds return-time recovery. An old backend that ignores the new field still completes by server-state verification after dismissal. Capture statuses and request identifiers without tokens or OAuth state.

## SSH setup and verification (SSH/node operators and PM)

Create/configure a certificate-mode SSH catalog service and its user connection using existing Web/CLI tools. Bind an online credential node. Configure its allowed principals, host and port; install the NyxID SSH user CA public key in the target's `TrustedUserCAKeys`, authorize the chosen principals and reload sshd. Upgrade the node binary to the matching backend's terminal signing protocol. Follow [SSH node/key authentication](../../docs/SSH_NODE_KEY_AUTH.md) and [node architecture](../../docs/NODE_PROXY_ARCHITECTURE.md).

Install the service's CA **public** key from the Web service detail page as `/etc/ssh/nyxid_ca.pub` on the target. In `/etc/ssh/sshd_config`, set:

```text
TrustedUserCAKeys /etc/ssh/nyxid_ca.pub
AuthorizedPrincipalsFile /etc/ssh/auth_principals/%u
```

Create `/etc/ssh/auth_principals/<unix-user>` containing the allowed certificate principal, one per line, with root ownership and no group/world write access. Validate with `sshd -t`, then reload sshd using the target OS's service manager. Keep an existing administrative session open while testing a new trust configuration. [SSH tunneling setup](../../docs/SSH_TUNNELING.md#3-target-machine-setup-passwordless-login) describes the Linux/macOS target steps.

Pre-seed/verify the cert-mode target host fingerprint with `nyxid node ssh cert-host-key pin <host> <port> <SHA256:fingerprint>`, or inspect the node's TOFU store `ssh_cert_host_keys.toml` after a trusted first connection. Use `nyxid node ssh cert-host-key list` to inspect pins. Investigate a mismatch before legitimate key rotation; `forget` is the explicit operator recovery, never an app bypass. Host-key mismatch/offline-node errors retain the server message.

Interactive Web and mobile terminals stay open while idle: the node sends downstream SSH keepalives every 15 seconds, allows at most three unanswered keepalives and detects dead peers within about 60 seconds, with no inactivity timeout. Upgrade `nyxid node` to receive this fix; older nodes retain the 30-second idle close. Exec, connection tests and other noninteractive paths keep their existing timeouts without keepalives. No server or API change is required. Verify an idle terminal remains usable beyond 30 seconds after the node upgrade; mobile backgrounding still follows the separate 15-second grace below.

Normal human `ssh_tunnel::session_connection` does not resolve UserService ids; the screen validates the selected `/keys/{id}` connection then uses its catalog id for `/api/v1/ssh/{catalog_id}/terminal`. Assistant credentials have a separate exact-connection resolver. Mobile opens the socket in RN with refreshed session and the same client headers as HTTP, retries one 401 after forced refresh and never puts credentials in a URL or WebView. RN 0.83 emits an empty socket error event and puts the native upgrade diagnostic in the following close reason; the adapter reads that reason before mapping 401/403/404/429/5xx or the network fallback. PTY permission is granted only to terminal sessions (Web and mobile terminal), via exactly `permit-pty`. Certificates issued through `POST /ssh/{id}/certificate` (`nyxid ssh proxy` / `issue-cert`) and for exec carry no extensions, as before; interactive `ssh` via `nyxid ssh proxy` remains PTY-less. No agent-forwarding, port/TCP-forwarding, X11-forwarding or user-rc extension is issued. Targets with `PermitTTY no` or `no-pty` principal options still refuse a PTY. Previously issued certificates are short-lived for the service TTL and simply expire; no revocation or target change is needed.

The offline renderer embeds xterm 6.0, fit addon 0.11 and JetBrains Mono 400 with their MIT/OFL notices. Settings → Support → Open-source notices displays those exact generated notices in a selectable monospace view. Regenerate with `node scripts/generate-terminal-assets.js`; `--check` verifies generated bytes. No file access is required. The inline document loads as `about:blank` on iOS (`loadHTMLString` with that base URL); its initial `other` top-frame request is permitted once, and load-start closes that allowance on platforms that do not call the request hook for the initial document. Further navigation and new windows are denied. CSP denies all network resources, including connections, images and frames; the only font is the bundled `data:` JetBrains Mono face, and only bundled inline scripts/styles execute. The terminal uses the immersive dark surface and Web's ANSI palette. The bridge is validated and bounded. RN batches binary output into at most 64 KiB base64 chunks, one acknowledged chunk in flight and at most 4 MiB queued; when a gap is required it drops oldest queued bytes, emits one visible localized marker, and keeps the shell alive. When a session ends, the terminal writes a dim localized close notice or the server error text, hides the cursor and blocks input until Reconnect establishes a new session. The screen closes the socket only after AppState reaches `background`; a 15-second grace is measured by wall clock, so a suspended JS timer cannot keep a session alive longer. Returning within the bound preserves the same session. This preserves terminal use while iOS reports `inactive` for transient system UI and while another route covers the terminal; unmount, account changes and Reconnect close it. The route's `serviceId` is the catalog service id used by the WebSocket; Services/Plugins also pass the exact `connectionId`, while a deep link resolves the user's active connection for that catalog id and offers Services when none exists. A valid user-selected principal survives Reconnect; a route principal is reapplied only when the parameter changes, with allowed route/single-principal fallback when a selection is removed. Renderer termination returns to an explicit Connect action with an informational notice; the replacement document cannot auto-connect. Attempts starting outside the active state defer the socket and start the same wall-clock background bound. Truncated paste uses an informational notice that clears on the next paste or connection attempt. Deep links show a pre-connect screen and never auto-connect; only the in-app Open terminal action sets the internal auto-connect flag. Non-certificate services explain the matching `nyxid ssh exec <service>` or `nyxid ssh proxy` command; paused certificate services must be enabled first.

On both platforms, verify principal selection, shell UTF-8 output, resize after rotation/keyboard changes, typing, Esc/Tab, sticky Ctrl-C, application-mode arrows (`vim`/`less`), punctuation and bracketed Paste. Verify 401/403/404/429/server upgrade errors, remote close, offline node and a deliberately mismatched host pin in a disposable test environment. Background starts a 15-second wall-clock grace bound: returning to active within it preserves the same pending or connected socket, while expiry closes it deterministically with code 1000 and shows Disconnected; unmount and Reconnect close immediately. Covering the terminal with Activity preserves the pending approval/socket and Activity's Back returns to the same terminal; the user decides the neutral request there, and an approval unblock continues that socket without a new attempt. Reconnect opens a fresh shell and never replays input. Capture proxy/device network traffic to confirm only RN opens the WebSocket and the WebView fetches no assets.

Under the default **Writes only** approval policy, opening a mobile terminal (`ssh:tunnel`) and SSH exec can each raise an approval for the same person. The mobile request authenticates with a Bearer access token (`requester_type: access_token`); the Web cookie session used by Web SSH bypasses these approvals. WS3 does not change authentication or approval semantics while the owner decision is pending. The mobile app keeps its pending socket alive while the user opens Activity and approves or denies the neutral request; Activity's Back returns to the terminal. An HTTP 403 after the attempt enters the waiting state uses non-asserting copy because RN WebSockets cannot read the upgrade response body: an approval may have been denied or expired, or access may have changed. An immediate 403 retains the permission-denied guidance. Server errors wrap in full below the compact status/actions row. Retry with Reconnect to request a fresh session.

## Automated verification

Use CI's Rust 1.98.1 toolchain (`rustup run 1.98.1 cargo`, equivalent to CI's `cargo +1.98.1`) and a running writable test MongoDB (the existing test helper selects the local development instance on port 27018; `NYXID_TEST_DATABASE_URL` can select an explicit test instance). Run `rustup run 1.98.1 cargo fmt --all -- --check`, `rustup run 1.98.1 cargo clippy --workspace --all-targets -- -D warnings`, and `rustup run 1.98.1 cargo test -p nyxid` filtered to the changed handler/service/model/config modules. Tests create isolated test databases. Set `RUST_MIN_STACK=8388608`, matching `.github/workflows/backend-tests.yml`, for the large async test futures. From `mobile/`, run `pnpm test`, `pnpm test:jest --runInBand`, `pnpm typecheck`, and `pnpm check:native-sync`. The Node suite also checks that generated offline terminal assets and MIT notices match the installed locked dependencies. `node scripts/generate-terminal-assets.js --check` can verify that contract directly.

The OAuth callback tests cover success, provider denial and malicious provider text, session mismatch, exchange/write failures, missing code, unknown fields and legacy redirects. Social login's existing scheme test stays unchanged, with a separate production Expo regression. Native tests cover account/expiry fences, old-backend dismissal, cold/warm link interception, both association host sets, push logout cleanup and backend payload parsing. Terminal tests execute the local bridge, validate its CSP and navigation policy, exercise native upgrade diagnostics, transport lifecycle, principal selection, resize, clipboard fencing and the credential boundary. Physical-device and external-provider results remain PM-owned.
